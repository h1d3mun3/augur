## 1. Essence

augur's egress control is unchanged at its core. It is a host-side, sudo-free, on-by-default domain allowlist enforced by `augur-proxy`, which runs as the ordinary host user and re-checks every connection by hostname against a union-only, three-layer allowlist. It denies IP literals, SNI-less connections and private destinations, and none of that code moved in this window. The guest has no direct route out:
- **Apple Container:** an `--internal` network with `--cap-drop NET_ADMIN` and `--no-dns`.
- **macOS VM:** one host-owned NIC fed through gvproxy's `--socks-upstream`/`--dns-allowlist`/`--deny-direct`, now pinned to upstream `757461b1`. The DNS gate still runs first, and every name type it admits now resolves through gvproxy's typed resolver; nothing falls through to a raw forward.

It fails closed at every layer. An unreadable allowlist stops startup, an empty one denies everything, an unreadable hot reload keeps the previous policy, and a live self-test tears the guest down if any direct probe gets out. On the macOS side (on the unmerged `fix/macos-setup-token-throwaway-clone` branch), each VM records the egress mode it was booted with, and augur refuses to attach to a running VM whose mode differs or is unknown instead of guessing. `setup-token --macos` now runs in a throwaway clone of the base VM. That clone has egress forced on, uses the baseline and global allowlist only, gets no credentials and no shares, passes the same boot self-test and a Team-ID-pinned signer check, and is deleted on every exit path.

### 2.2 Custom CA trust (`augur install-cert`)

**Unchanged, and still no effect on the egress boundary.** The `augur-proxy/` tree hash matches the baseline, so the previous snapshot's finding still holds without re-deriving it. The proxy decides by hostname from the ClientHello before guest TLS runs, and it never decrypts. A CA in the guest trust store cannot change that decision. What it does change is who can read the TLS of allowlisted hosts. That is why the command is explicit and gated, and `confirm_cert_install`'s own warning says the same (`:3145-3147`).

Current anchors (all three bodies are identical to `b65e412`):

### 2.5 Workspace containment

**This guard is shared by both engines, so it is described once here and not repeated for Container.** `require_safe_workspace()` (`augur:1453-1493`) refuses a workspace that:

- is `/`;
- is `$HOME`;
- contains `$HOME`;
- is, contains or lives inside `$AUGUR_DIR`.

The reason is that the workspace is shared read-write into the guest. A guest that can write `~/.augur` could replace the binaries the host executes and edit the merged allowlist that `augur-proxy` hot-reloads. The refusal prints the resolved path and offers `augur destroy` for an older guest (`:1483-1491`, `exit 1` at `:1492`). **The function is code-identical to `b65e412`** (comment-stripped body diff; it moved from `:1367` to `:1453`).

**Mechanics, re-read:**
- Paths are compared physically. The workspace and `$HOME` are resolved with `cd … && pwd -P` (`:1455-1458`).
- `$AUGUR_DIR` is resolved through its parent, so a first run with no `~/.augur` still compares something (`:1462-1467`).
- The branches are `/` (`:1471`), `== $HOME` (`:1473`), `$HOME` inside the workspace (`:1475`), and the three `$AUGUR_DIR` relations (`:1477`).

**The call site changed.** `setup-token --macos` is now excluded (`fd02a76`). The dispatch tail (`augur:6217-6220`) is now:

```bash
esac
```
