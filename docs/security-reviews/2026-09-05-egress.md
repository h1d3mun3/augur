## 1. Essence

augur egress control is still a **host-side, fail-closed, on-by-default domain allowlist** that
confines a possibly prompt-injected coding agent by forcing all guest outbound traffic through
**augur-proxy**, a sudo-free Swift forward proxy running as the ordinary host user, which re-resolves
each connection by hostname and admits it only against a union-only, three-layer allowlist; the same
contract is shared, byte-for-byte on the DNS-matching side, across both engines. That shape is
unchanged by this cycle. What is different from 2026-07-28 is that the macOS engine is now
**simpler, not more capable**: the mitigation for a virtiofs staleness defect that had grown into a
long-lived host-side process, a guest round-trip surface, and a new operator-facing dial has been
withdrawn in full ([ADR-0017](../decisions/0017-accept-virtiofs-staleness.md)) in favor of accepting
the underlying platform defect and documenting the remedy (`down --macos && up --macos`) — a
reduction in surface, not a weakening of enforcement, since the withdrawn mechanism never touched the
egress datapath in the first place. The two engines' enforcement elements — host-only gateway bind
and `--no-dns`/`--cap-drop` on Apple Container, gvproxy's `--dns-allowlist`/`--deny-direct`/SOCKS
forcing on macOS — are otherwise exactly as they were, with one gvproxy-side fix landed the same day
this snapshot was taken: the SOCKS dial path now carries a connect timeout, closing an availability
gap (a hung upstream could starve all guest egress) that a routine upstream repin had introduced and
same-day review caught before it reached a released tag.

## 2. Enforcement boundary per engine

Both engines share the same merged allowlist and the same augur-proxy filter core; they differ in
where the proxy runs and how the guest is severed from direct egress. This cycle's changes landed
almost entirely on the **macOS VM** side — the entire #124/#135 virtiofs-staleness mitigation
(share-refresh loop, freshness tripwire, `warn`-on-profile-edit) that the 2026-07-28 snapshot
described in its §2.4 was **reverted** after this snapshot's baseline (see "What changed", above),
leaving only a gvproxy repin, a SOCKS dial-timeout fix and the `gh-config` share removal on that
engine (detailed in §2.4). **Apple Container is untouched by any commit in range**: `git diff --stat
3b7cd1e..HEAD -- augur-proxy augur.conf` is empty, and every line the subsections below cite in
`augur` is unmoved or shifted by exactly the same constant offset as the rest of the file above the

### 2.1 Base-image custom provisioning

Unchanged since 2026-07-28, re-verified at `augur:95-114` and `:4580-4653`. An operator can
pre-install extra packages into augur's *shared*, host-global container image at build time via
`~/.augur/provision/container-packages.conf` (a flat apt package-name list), gated end to end:
presence is checked for actual non-comment content (`provision_container_packages_present`,
`augur:4589-4592`, so an untouched scaffold template adds no `--build-arg` and no prompt), each
line is validated as a bare package name (`provision_container_packages_validate`, `:4594-4603`),
and the file is TOFU-approved by content hash before it can affect a build
(`check_container_provision_approved` → `tofu_decide`, `:4619-4622`); `container_provision_prepare`
(`:4633-4637`) runs both checks and is required to be called **directly**, never inside a `$(...)`
subshell, because an `exit` there would otherwise only kill the subshell and let an unapproved
build proceed (`:4625-4632`) — the same pitfall the project allowlist gate guards against
elsewhere. Approved packages become one `--build-arg EXTRA_APT_PACKAGES=…` (`:4645-4652`), consumed
by both `cmd_build` (`:1653`) and `cmd_install_cert` (`:2453`).

**This manifest is materially simpler than its macOS counterpart, and the code says so
explicitly** (`augur:4582-4585`): `container-packages.conf` packages are baked via a one-shot
`eng build`, and that build **already runs with zero egress filtering, pre-existing and
unchanged** — there is no dedicated proxy/gvproxy pair standing over it the way macOS's `hook.sh`
runs over one. So, unlike the macOS root-hook script (which executes arbitrary shell as root
against a build-time egress allowlist), the container manifest is a closed, structurally-limited
grammar (bare `apt` package names only, `provision_package_name_valid`) with no code-execution
surface of its own, and its trust boundary is simply "the image build's network is unfiltered by
design" rather than "an allowlisted egress hole." **No test file references any of
`container-packages.conf`, `provision_container_*` or `provision_package_name_valid`**
(`grep -rl` over `tests/*.sh` returns nothing) — this path is TOFU-gated and grammar-checked in
code but exercised by no offline or live test, the same "residual, not a gap in intent" posture
the previous snapshot recorded for the macOS hook (§6 item 11 there).

### 2.2 Custom CA trust (`augur install-cert`)

Unchanged, and still inert to the egress boundary — re-verified by grep against the current tree
rather than resting on byte-identity: `grep -rniE 'tls|ssl|certific|x509|trust' augur-proxy/Sources`
returns no TLS-termination site, only ClientHello *parsing* (`SNI.swift:3`, "we never decrypt"),
the CONNECT blind-tunnel comment (`ProxyRequests.swift:22`) and a "not a TLS record" method-line
check (`:64`) — confirmed unchanged because `augur-proxy/` has an identical tree hash
(`065670cb…`) at both ends of the range. A guest-trusted CA therefore only ever affects what the
guest's *own* TLS clients accept **after** the proxy's tunnel is established; the proxy's
by-hostname allow/deny decision happens earlier and cannot be influenced by trust-store content.

`cmd_install_cert` (`augur:2436-2469`) base64-encodes the cert and re-runs the same
`container_provision_prepare` / `container_provision_build_args` path as §2.1
(`augur:2454`, `:2456`) with an extra `--build-arg AUGUR_CA_CERT_B64=…`, so an `install-cert` also
picks up any approved `container-packages.conf` in the same build. It still rejects a trailing
`--macos` so a cert meant for the VM cannot be silently baked into the Linux image instead
(`:2440-2445`), still warns that the image tag — and therefore the trust — is shared by every
project on that Swift tag (`:2449-2450`, `:2467`), still warns that a later `build`/`update`
rebuilds the image clean and **drops** the CA (`:2466`), and still invalidates this project's
persisted container so the rebuilt image actually takes effect on the next `up`
(`invalidate_persisted_container`, `:1668-1677`, called at `:2468`). `tests/05_install_cert_unit.sh`
is byte-identical to the baseline (`e75e779c…` both ends) and passes 7/7 in this checkout.

### 2.3 Container lifecycle: persist-and-reconcile

Unchanged since #114/#128; re-derived at the current tip, not copied forward:

- **`down` STOPS and keeps** the container and its egress network (`cmd_down`, `augur:2315-2341`;
  the network is deliberately kept — only `stop_proxy` runs, at `:2340`, no network teardown).
- **`up` on a stopped container** re-ensures the network, `eng start`s it, then runs `finish_up`
  (`augur:2012-2020`).
- **`up` on a RUNNING container reconciles** rather than no-opping (`augur:1976-2001`): the TOFU
  gate (`:1979`), a deliberately redundant `write_merged_allowlist >/dev/null` so a revocation
  lands even on the refusal path (`:1983`), a hard `exit 1` on `! container_fingerprint_matches`
  (`:1994-1998`, since `--network`/`--cap-drop`/`HTTP_PROXY`/`--no-dns`/credentials are baked once
  at `container run` and cannot be re-applied to a running container), then `finish_up`
  (`:1999`, still commented "restores I1's boot self-test on this path").
- **`finish_up`** (`augur:1938-1958`) is the single place all three `up` paths converge: under
  `egress_enabled` it calls `start_egress_proxy` then `verify_egress_locked` (`:1939-1942`) before
  anything else, so the boot tripwire cannot be delayed or masked by the profile-apply step that
  follows it.
- **`container_fingerprint`** (`augur:1703-1745`) hashes egress mode, the *stable* wiring inputs
  (subnet, gateway override, proxy port — not the live-inspected gateway, to avoid false
  mismatches), memory, workspace/mount paths, the profile mount path, every resolved auth value,
  and `gh auth token` — anything baked into `container run` argv that can't be changed on a running
  or persisted container without recreating it.
- ***Caveat carried forward, still INFERRED and still not exercised — no container engine is
  available in this environment:*** the fingerprint does **not** cover `egress_network_name()`
  (`augur:1210`), and both `AUGUR_INTERNAL_SUBNET` (`:73`) and `AUGUR_PROXY_HTTP_PORT` (`:80`)
  retain `${VAR:-}` override forms — so an operator who pins both would see an unchanged
  fingerprint and no recreate, while `ensure_egress_network` (`:1216`, which checks existence **by
  name only**) creates the new hash-named network alongside the old one. It may fail loudly on a
  duplicate subnet rather than diverging silently; still untested for the same reason as before.

**What mechanically enforces the boundary, restated against the current tree.** The containment
argv built under `if egress_enabled` (`augur:2051-2071`) is: attach to the per-project host-only
`--internal` network (`--network "$(egress_network_name)"`, `:2055`, created `--internal` at
`:1221`, so it has no external route at all); `--cap-drop NET_ADMIN` (`:2056`, root-in-guest cannot
re-route); `HTTP(S)_PROXY` pointed at the host-only gateway (`:2057-2059`); and `--no-dns`
(`:2069`, empty `/etc/resolv.conf`, no resolver to smuggle a query through). On top of that argv,
`verify_egress_locked` (`augur:1300-1344`) runs on **every** `up` via `finish_up` and is the live
backstop: it probes seven distinct direct-egress targets (IPv4 and IPv6, ports 80/443) with the
guest's `PATH` pinned to system dirs so a persisted guest's `~/.local/bin` cannot shadow `curl`
(`:1309-1319`), probes that external DNS resolution fails (`:1323-1326`), and probes that the proxy
itself answers an HTTP status through the configured `-x` proxy (`:1330-1336`); **any** leak sets
`leaked=true` and the guest is force-removed and egress torn down before `exit 1` (`:1337-1342`) —
this is the mechanism, not the argv alone, that makes a container in a bad state unusable rather
than silently insecure.

**What is documented but not enforced, re-measured at this tip rather than assumed carried
forward.** `INVARIANTS.md`'s I5 and I8 both flag that the containment argv itself is asserted by no
test, and this snapshot re-ran the mutation rather than trusting the prior one: deleting
`run_args+=(--no-dns)` (`augur:2069`) and, separately, replacing `--cap-drop NET_ADMIN` (`:2056`)
with a no-op, each still leave `bash tests/run.sh` **ALL GREEN (26 scripts)** in a fresh
`git archive HEAD` export — the same result the baseline recorded for M4 on the pre-revert tree.
The structural reason is unchanged too: every offline container-construction test drives
`up --no-egress` (`tests/11_construct_container.sh:28,90,105,116` and others), so the
`if egress_enabled` block that builds this argv never executes offline at all; `tests/22`, the one
suite that would exercise it against a real bind, self-skips without `AUGUR_TEST_LIVE=1`
(confirmed this run: `0 passed · 0 failed · 1 skipped`, no container engine in this Linux
environment). `INVARIANTS.md:122-126` (I8's note) and `:79-80` (I5's note) already say this
plainly; `INVARIANTS.md` itself is byte-unchanged over this range (no invariant's text, `Enforced
by` line or severity mark moved), so nothing in this cycle changed it in either direction.

**The rebase surfaced a real gap, caught by code review and fixed same-day.** Upstream's own hunk
threaded its new `connectTimeout` into `forwarder.TCP`'s direct-dial branch
(`gvproxy/augur-egress.patch`, `pkg/services/forwarder/tcp.go`: `net.DialTimeout("tcp", target,
connectTimeout)`), but augur's SOCKS branch — the one augur actually runs in production, since
`--socks-upstream`+`--deny-direct` are always passed together (`augur:1447-1452`) — called
`socksDial(socksAddr, dst, port)` with no timeout parameter at all pre-fix. `423a7d4` ("apply
connectTimeout to the SOCKS dial path too") threads `timeout time.Duration` through
(`gvproxy/augur-egress.patch:499`): `socksDial` now opens with `net.DialTimeout("tcp", socksAddr,
timeout)` (`patch:500`) in place of a bare `net.Dial`, sets an overall
`c.SetDeadline(time.Now().Add(timeout))` (`patch:510`) covering the SOCKS greeting/request/reply
exchange, and clears the deadline (`c.SetDeadline(time.Time{})`, `patch:574`) once the handshake
completes so the bound does not apply to the actual proxied data afterward. Without it, a hung or slow augur-proxy — or a TCP peer
that accepts but never speaks SOCKS — blocked the dialing goroutine forever, pinning one of
`TCP()`'s `maxInFlight` forwarder slots; enough hangs exhaust the pool and stall all guest egress. Not
an allowlist bypass (the hang is *before* any data crosses the boundary), but an availability defect
in the enforcement path itself. Verified by reading the current patch, not by inference: the call site
in `services.go` is `forwarder.TCP(s, translation, &natLock, configuration.Ec2MetadataAccess,
configuration.TCPMaxInFlight, time.Duration(configuration.TCPConnectTimeout)*time.Second,
configuration.SocksUpstream)` (`gvproxy/augur-egress.patch`, `pkg/virtualnetwork/services.go`), so the
same `connectTimeout` that already bounded the direct-dial branch is now the one value threaded into
both. **One thing this review could not verify:** augur never sets `TCPConnectTimeout` explicitly in
`GvproxyConfigure` (`grep -n TCPConnectTimeout gvproxy/augur-egress.patch` shows only the type
declaration and its threading, no augur-side assignment), so the actual deadline `socksDial` now
enforces comes entirely from gvproxy's own upstream default — a concrete value this review did not

### 2.5 Workspace containment

**Unchanged since 2026-07-28, and — as that snapshot noted — this mechanism is not engine-specific:
it is written once here rather than described twice, once per engine, because it is the same function
and the same call site gating both.** `require_safe_workspace()` (`augur:974-1014`) refuses a
workspace that **is**, **contains**, or **lives inside** `$HOME` or `$AUGUR_DIR` (or is `/`), by
comparing **physical** paths (`pwd -P`, `:976-988`) so a logical symlink cannot dodge the check. It is
gated at a single dispatch-tail call site shared by both engines — `case "$COMMAND" in
up|claude|shell|setup-token) require_safe_workspace ;; esac` (`augur:4936`, was `:5433` at the
predecessor's tip; the shift is entirely from the #152 revert removing code above it) — deliberately
excluding `down`/`destroy`/`list`/`status`/`build`/`update`/`install-cert`, so a guest a pre-fix augur
created from `$HOME` remains removable
([ADR-0014](../decisions/0014-workspace-must-not-contain-augur.md)).

The mechanism it closes, stated in-code at `augur:962-973` (one line up from the predecessor's
`:962-975` — again a pure offset from the revert, not a content change): `$WORKSPACE_DIR` is shared
**read-write** on both engines and `install` puts `~/.augur` first on the host's PATH, so a guest that
could write into `$HOME`/`$AUGUR_DIR` could plant a binary the host user's next `augur` invocation
resolves and executes; secondarily, `WORKSPACE_DIR=$HOME` would put the merged allowlist under
`~/.augur/proxy` inside the read-write share, which the in-code comment calls "a direct I7 violation."
The function deliberately does not re-base `WORKSPACE_DIR` on the resolved physical path (comment at
`:967-973`, immediately above the function): `workspace_path_hash` feeds container names, VM names,
the TOFU approval key and every per-project state directory, so re-basing would silently rename all
per-project state for anyone whose path crosses a symlink — the physical resolution (`pwd -P` at
`:976,978,983`) stays local to this function's own comparison. There is deliberately no escape hatch:
relocating `AUGUR_DIR` is an unconditional assignment (`augur:41`, unaffected by this cycle) and does
not disable the guard.

### I7, in full

**Rule** (`INVARIANTS.md:89-96`, unchanged this cycle — `docs/security-reviews/` has an empty diff
against baseline): the merged allowlist is written host-side outside the project tree; a project's
`./.augur/allowlist.conf` is merged only after TOFU approval and only its sanitized domains; every
per-project egress host-state file is keyed on the **full workspace path**, so one project's approval
can never reach another's live proxy.

- **Written outside the project tree:** established above — `proxy_allowlist` resolves under
  `$AUGUR_DIR/proxy`, and that directory is not among the four macOS `--dir=` shares nor the
  container's single read-write bind (`-v "${WORKSPACE_DIR}:…"`, container mode's only guest-writable
  mount).
- **Sanitized before merging:** `write_merged_allowlist` never touches the live `AUGUR_PROJECT_CONF`
  directly — it reads only `$(project_conf_hash_file).domains`, a file that `write_project_snapshot`
  (`:817-819`) populates exclusively from `project_conf_domains`'s output, i.e. already
  `conf_line_valid`-filtered. There is no code path from the guest-writable file to the merged
  allowlist that skips that gate.
- **Full-workspace-path keying:** `proxy_allowlist`, `project_conf_hash_file`, `proxy_pidfile`,
  `proxy_logfile`, `gvproxy_socket`/`gvproxy_pidfile`/`gvproxy_log`, and `macos_vm_log` are all
  `$(workspace_slug)-$(workspace_path_hash)` (`augur:681-688,943-950,1020-1023,1377-1383`) — never
  slug alone. The comment at `:683-687` states the failure this prevents by name: two same-basename
  projects (`~/work/app`, `~/archive/app`) sharing one merged allowlist, "whichever ran last" owning
  both projects' egress.

### Summary

The dominant fact this cycle is a **subtraction, not an addition**: ADR-0017 removed the entire
virtiofs shared-file-cache-refresh mechanism the 2026-07-28 snapshot devoted a third of its length
to, because the mitigation's own defects (a silent tripwire, a forgeable report, a dead subshell
guard ahead of the I1 teardown, a 31-hour-silent seam bug) kept costing more than the staleness it
mitigated. Items 36–41 are **closed by removal**, not by fix — the underlying platform defect
(#124/#135) is still open and now documented-and-accepted instead. Six other items (8, 12, 22, 27,
28, 30, 31, 35) shed a 2026-07-28 addendum each and revert to their pre-2026-07-28 substance; two of
those reversions are notable enough to name explicitly: item 26 and item 31 both went "immediately
before / exactly three traps" → "no longer immediate / four traps" → **back to "immediately before /
exactly three traps,"** re-verified fresh both times rather than assumed. Item 24, the one real open
defect in this whole area (the macOS reconcile-path self-test's missing `egress_enabled` guard), is
unaffected by any of this — still open, still unfixed, still reachable via `augur up --macos
--no-egress` against an already-running VM — but its blast radius shrinks back to two unconditional
steps ahead of the tripwire instead of the five 2026-07-28 measured. Item 32, the complete absence of
any test guarding the production containment argv on either engine, is untouched by this cycle (the
code is byte-identical) and remains the single biggest assurance gap in the contract. The one new
piece of code in this area — the gvproxy repin plus its same-day SOCKS-timeout fix — closes a real
availability gap the rebase introduced, cleanly, but leaves one narrow tail (the actual timeout
value) unverified in this environment (item 43); everything else in the repinned patch that matters
to egress (`--dns-allowlist`'s qtype gate, `--deny-direct`'s UDP/ICMP/mux suppression) was diffed and
found byte-identical to the pre-repin baseline. `augur-proxy/`, `augur.conf` and `augur-vm/` remain
byte-identical to the 2026-07-28 baseline throughout. The honest frame is unchanged from every prior
review: no live macOS guest ran in this one either — `tests/e2e_macos_vm.sh` is the only live gate
and was not exercised — so everything macOS-specific above rests on a bash stand-in for `ssh_macos`,
on reading, and on the offline suite (26 scripts, 753 assertions, 0 failed this run), not on a
booted VM.
