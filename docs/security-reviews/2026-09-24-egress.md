## 1. Essence

augur's egress control is still a host-side, sudo-free, on-by-default domain allowlist. augur-proxy runs as the ordinary host user and re-checks every connection by hostname against a union-only, three-layer allowlist. It denies IP literals, connections without SNI, and private destinations. The guest has no direct route out. On Apple Container, that is an `--internal` network with `--cap-drop NET_ADMIN` and `--no-dns`. On the macOS VM, it is gvproxy's `--socks-upstream`/`--dns-allowlist`/`--deny-direct`, now pinned to upstream `fc319b8f`. It fails closed at every layer: an unreadable allowlist stops startup, an empty one denies everything, and an unreadable hot reload keeps the previous policy. A live self-test runs on every `up` path and tears the guest down if any direct probe gets out. This cycle's one material change sits beside the boundary rather than in it: Container-mode credentials are no longer baked into the persisted container. They go only into each `augur claude`/`augur shell` session, through a builtin-written `--env-file` pipe. Invariant I10 is now test-enforced for Container mode, and its accepted exception is limited to the macOS guest admin password.

## 2. Enforcement boundary per engine

The two engines still share one merged allowlist and one `augur-proxy` filter core. `augur-proxy/`'s tree hash moved this cycle (`065670cb…` → `96f96028…`), but every changed hunk in `git diff e1f00be..HEAD -- augur-proxy` is a comment (§3). What differs between the engines is how the guest is cut off from direct egress. Apple Container does it at the network layer: the container sits on an `--internal` host-only network with no resolver, its proxy env points at a host proxy bound to that network's gateway, and a live boot self-test deletes the container on any leak. The macOS VM does it with a single host-owned NIC socket fed through gvproxy (SOCKS-forced TCP, `--dns-allowlist`, `--deny-direct`). **The previous snapshot called the Container half untouched. That is no longer true.** In `e1f00be..HEAD`, `ea55148` split `cmd_up` into reconcile / reuse / recreate. `777c85a` moved every injected credential and `TZ` off `container run` and onto the session `exec`, removed credentials from `container_fingerprint`, and added an Apple Container CLI 1.0.0 floor. `6054f1c` documented that the boot self-test depends on `sh -c`. `tests/11_construct_container.sh`, `tests/22_egress_failclosed.sh` and `tests/32_proxy_per_mode.sh` all changed blobs (22 and 32 only in comments). Everything below was re-derived at `HEAD` (`6054f1c`). Tests were run on a Darwin 27.0.0 arm64 host with **no Apple Container CLI installed** (`command -v container` finds nothing), so every live Container tier self-skipped.

### 2.1 Base-image custom provisioning

The logic is unchanged since the baseline. The line numbers moved, and one caller was missing from the previous snapshot. `~/.augur/provision/container-packages.conf` goes through three checks before it can affect the shared, host-global image:
- a content-presence check, so an untouched scaffold adds no `--build-arg` and no prompt (`provision_container_packages_present`, `augur:4946-4949`);
- a closed-charset check on every line (`provision_package_name_valid`, `augur:4457-4459`, shared with the macOS manifest grammar; applied by `provision_container_packages_validate`, `:4951-4960`);

That unquoted expansion is safe only because of the host-side charset check.

There are **three** callers, not the two the previous snapshot listed: `cmd_build` (`augur:1805-1809`), `cmd_install_cert` (`:2683-2686`) and `cmd_update` (`:2762-2766`). An implicit first build from `cmd_up` → `ensure_image` (`:387-392`) goes through `cmd_build`, so it gets the same gate.

### 2.3 Container lifecycle: persist-and-reconcile

**The mechanism changed this cycle, not just the comments.**

**The `cmd_up` split (`ea55148`).** `cmd_up` (`augur:2399-2434`) now dispatches three ways:
1. **Already running:** `reconcile_running_container` (`:2123-2138`).
2. **Stopped with a matching fingerprint (reuse):** handled inline (`:2421-2431`). The commit message and the code agree on why it stays inline: extracted and called as an `if` condition, `start_egress` and `finish_up`'s self-test would run with errexit disabled.
3. **Otherwise:** `recreate_container` (`:2158-2218`). The `run` argv is built by `_add_egress_run_args` / `_add_state_mount_run_args` / `_add_host_config_run_args` (`:2221-2307`).

The commit claims the argv is byte-identical and that `tests/11` asserts the exact argv. **That second claim does not cover the egress block.** Every `up` in `tests/11` runs `--no-egress` (`:31`, `:105`, `:120`, …). I checked the egress block by diffing its `run_args+=` lines against `e1f00be`. `--network`, `--cap-drop NET_ADMIN`, the six proxy `-e` values and `--no-dns` are identical in content and in order. The only removals are `-e TZ=…` and the per-credential `-e`.

**Per-session credentials (`777c85a`).** Nothing credential-shaped and no `TZ` is baked at `run` any more (`:2182-2183`). Credentials reach only the `exec -it` that starts `claude`/`shell`, as `--env-file <(session_credential_env)`:
- `session_credential_env` is at `:2331-2345`; the call sites are `:2459` and `:2480`.
- `TZ` and the `GIT_CONFIG_*` helper are plain per-session `-e` (`_add_session_exec_env`, `:2360-2369`).
- `setup-token`'s exec gets no `--env-file` (`:2523`).

This changes three things the previous snapshot said:

1. **`container_fingerprint` (`:1874-1908`) no longer hashes credentials or `gh auth token`.** It now covers only:
   - egress on/off;
   - the stable wiring inputs (subnet, gateway override, proxy port);
   - memory;
   - workspace and mount paths;
   - the profile mount path;
   - whether `~/.gitconfig` exists.

   A rotated or removed credential now reuses the stopped container (`tests/11:141-151`). Every pre-upgrade container recreates once, because its old fingerprint no longer matches.
2. **The reconcile refusal comment no longer lists credentials as baked** (`:2140-2141`). The list is now `--network`/`--cap-drop`/`HTTP_PROXY`/`--no-dns`/`--memory`/mounts.
3. **`claude`/`shell`/`setup-token` on an already-running container now check the fingerprint** (`require_running_container_current`, `:2149-2154`, via `ensure_session_container` `:2377-2383` and `:2500`). At `e1f00be` they ran `container_running || cmd_up`, with no fingerprint check. One consequence: a container still running from an earlier `up --no-egress` fingerprints as `egress=off`. A later default (egress on) `augur claude` against it now refuses instead of opening a session in an unfiltered guest. `tests/11:462-481` pins the refusal (non-zero exit, no `exec -it`, no env-file) using a corrupted fingerprint rather than an egress-mode flip. This path still does not re-run `finish_up`, which is the same as the baseline.

**Still true from the baseline:**
- **`down` stops and keeps** the container and its network. Only `stop_proxy` runs (`cmd_down`, `:2544-2572`, `stop_proxy` at `:2571`).
- **`destroy`** (`:2577-2593`) force-removes the container, deletes the fingerprint (`:2587`), drops carried-over history (`:2591`) and runs `stop_egress`. `stop_egress` (`:1416-1425`) also reaps the pre-hash legacy network name (`:1424`).
- **Reuse** re-ensures the network, runs `eng start`, then `finish_up`. A start failure falls through to a clean recreate (`:2426-2433`).
- **Running reconcile** re-runs the TOFU gate and the deliberately redundant `write_merged_allowlist` (`:2126`, `:2130`) *before* the fingerprint refusal (`:2136`), so a revocation still lands on the refusal path.
- **Recreate** tears egress down if `eng run` fails (`:2200-2204`), writes the fingerprint (`:2207`), then calls `finish_up` (`:2217`).
- **All `up` paths converge on `finish_up`** (`:2100-2120`), which runs `start_egress_proxy` → `verify_egress_locked` under `egress_enabled` (`:2101-2104`), before `apply_guest_profile`.

**The subnet/port caveat is restated.** The previous snapshot's version ("creates a second, hash-named network") does not match the current code:
- `egress_network_name` (`:1339`) is slug plus path hash, and the fingerprint already covers `workspace=`.
- `AUGUR_INTERNAL_SUBNET`/`AUGUR_PROXY_HTTP_PORT` overrides (`augur:79`, `:82`) are in the fingerprint's `wiring=`, so changing them *does* force a recreate.
- The actual gap: `ensure_egress_network` (`:1345-1358`) only checks that the name exists, so a recreate re-attaches to the old-subnet network. `container_egress_gateway` (`:1373-1386`) then reads the live gateway from that network, so the baked `HTTP_PROXY` and the proxy bind stay consistent with each other.
- Net effect: the subnet override is silently ignored until `destroy`. Both networks would be `--internal` (`:1350`), so this is a usability issue, not a boundary issue.
- This is inferred from code only. No engine was available to exercise it.

The effect is also limited to domains an operator once approved for this exact path: it cannot import unapproved domains or another project's domains. What it weakens is revocation by deletion.
- **Fix:** deleting `$snap_file` on the early-return path would close it.
- **Coverage:** no test covers it.

### New this review

46. **[LOW–MEDIUM, assurance; re-opens item 21's mitigation] The boot self-tests' PATH pins act
    after the step that picks which program runs, on both engines.** The failure mode is the same
    on both: a prior guest session plants a stub, and the self-test then reports "isolated" no
    matter what the network does.
    - **Container** (from source; not measured live):
      - `apple/container`'s `ContainerExec` starts from the container's init-process config and
        *appends* exec `-e` (`ContainerExec.swift:59-67`).
      - The runtime passes `[executable] + arguments` with that env (`RuntimeService.swift:1268-1269`).
      - `vmexec` resolves a slash-less `argv[0]` through `Path.findPath`, which returns the
        **first** `PATH=` (`containerization` `vminitd/Sources/vmexec/vmexec.swift:91-92`,
        `Sources/ContainerizationOS/Path.swift:75-80`). That is the baked image PATH, which puts
        `/home/dev/.local/bin` first (`Dockerfile:48`).
      - So `-e PATH="$_probe_path"` (`augur:1452,1458,1465`) pins `curl`/`getent` *inside* `sh`,
        but not `sh` itself. A uid-1001 `~/.local/bin/sh` persisted across `down`/`up` runs for
        every probe. It can return non-zero for the direct and DNS probes and print `403` for the
        proxy probe.
      - `6054f1c`'s new comment (`:1443-1447`) correctly explains why a *genuine* shell sees
        clean env. That this shell is genuine is exactly what is not guaranteed.
      - The fresh-create path is unaffected (pristine image). The reuse and already-running paths
        are exposed.
      - Cheap fix: invoke `/bin/sh` by absolute path. `vmexec` then takes its absolute-path branch
        (`vmexec.swift:80-82`) and never consults PATH.
    - **macOS** (verified on this host):
      - `ssh_macos` runs the probe string under the guest user's zsh, which sources `~/.zshenv`
        *before* the command. That file is guest-user-writable; augur itself appends to it
        (`augur:3858`).
      - A function defined there shadows `curl`, `dig`, `dscacheutil` and `ping` despite
        `export PATH=…` (`:1669`). It shadows even an absolute path: zsh accepts
        `function /usr/bin/curl {…}`.
      - Reproduced with a scratch `ZDOTDIR`: `zsh -c 'export PATH=/usr/bin:…; curl …'` printed the
        function's output and rc 7, and `zsh -c '/usr/bin/curl --version'` printed the fake.
      - A kept clone is exposed on every later boot and on the reconcile path.
      - There is no cheap in-guest fix: anything the ssh transport runs has already passed
        through a guest-controlled startup file.
    - **Why not higher:** as item 21 always said, this blinds *detection*, not enforcement. The
      enforcement is host-side and independent of the guest: `--internal`/`--cap-drop`/`--no-dns`
      and augur-proxy on Container, and gvproxy's `--socks-upstream`/`--dns-allowlist`/
      `--deny-direct` on macOS.
    - It does mean item 21's "Mitigated" and item 20's compensating-control framing overstate the
      evidence the reuse-path tripwire provides. Not filed.
47. **[LOW–MEDIUM, not egress; newly recorded, code pre-existing] The setup-token integrity gate,
    item 20's other compensating control, can be spoofed by a persisted guest on both engines.**
    - **Container:** `agent_verify_integrity_engine` (`augur:504-509`) runs
      `eng exec "$CONTAINER_NAME" sh -c 'sha256sum "$(readlink -f "$(command -v claude)")"'` with
      **no** PATH pin at all.
      - With `~/.local/bin` first in the baked PATH, a planted `~/.local/bin/sha256sum` (or `sh`,
        per item 46) prints the image's hash.
      - `cmd_setup_token` (`:2506`) then attaches `~/.local/bin/claude setup-token` (`:2519-2523`)
        to the operator's TTY.
    - **macOS:** `agent_verify_integrity_macos` (`:515-517`) runs
      `codesign -dvv … | grep -qi "Anthropic"`. It runs under the same guest-sourced `~/.zshenv`
      as item 46. It is also a substring match over output whose `Identifier=` line is
      attacker-chosen for an ad-hoc signature.
    - **What it buys an attacker:** a lookalike login TUI in the one flow whose output the operator
      pastes back into the host. The host saves that token and injects it "into every future
      guest, in every project" (`setup_token_security_notice`, `:492-496`).
    - #212 made this flow run with no credentials in the guest, which removes the in-session
      `GH_TOKEN` channel. It does not remove the substituted-or-captured-token risk.
    - A PATH-pinned, absolute-path hash (`/usr/bin/sha256sum` under `/bin/sh`) closes the
      Container half. The macOS half has item 46's ssh-transport limit. Not filed.

### Summary

The dominant fact this cycle is a **closure**. PR #212 moves Container-mode credentials off
`container run`, and therefore off its argv and out of the persisted bundle, onto a per-session
`--env-file` pipe. That closes the long-accepted M1 (item 6). It is test-enforced offline, and I10 is
re-scoped to match. It has a bounded remainder: legacy bundles persist until recreated, and the "not
persisted" claim is pinned only by a live test this review could not run. #212 merged to `main` on
2026-09-24 (`08cb098`), after this review ran, with a tree identical to the one reviewed. The gvproxy
repin to `fc319b8f` was checked against pristine upstream source and only tightens DNS behavior. The
`augur-proxy/` tree-hash move is comment-only. Two genuinely new findings (items 46 and 47) share a
root the cycle's own duplicate-env measurement brought into view. The self-test's PATH pin and the
setup-token integrity gate are both the recorded compensating controls for the persisted-guest
foothold, and a stub planted by a prior session can defeat both on both engines. Container resolves
the executable from the *first* (baked) PATH. macOS's ssh transport runs through a guest-writable
`~/.zshenv`. Both findings blind detection or a login flow and open no route around the host-side
allowlist, and the Container halves have cheap absolute-path fixes. Item 24 (unguarded
reconcile-path self-test), item 32 (no test guards the enforcing argv on either engine) and item
44 (admin password on `ssh` argv, now an accepted residual named in I10) remain open and
unchanged. As in every prior review, no live container engine or macOS guest ran here.
