## What changed in the contract

`git log 70c5061..baccfcd -- docs/security-reviews/INVARIANTS.md` lists `ca2ebf8`, `38f5a89` and
`baccfcd`; the net diff is confined to I10 and the closing summary.

- **`**Rule:**` (`INVARIANTS.md:161-183`).** Before: on macOS the credentials are written to
  `~/.augur-env` via SSH stdin by `push_macos_guest_env` on every `up` / `claude` / `shell --macos`. Now:
  in macOS VM mode they reach the guest **only as the environment of the interactive ssh** that starts
  `augur claude --macos` / `augur shell --macos` (`ssh_macos_session`). A subshell `export`s the values
  and execs that one `ssh`, which names exactly the resolved variables with `-o SendEnv=<NAME>` (never
  `-o SetEnv=NAME=value`). The guest's sshd accepts exactly those names through a root-owned drop-in that
  the base VM build/update writes (`install_macos_session_env_acceptance`). A guest without it is refused
  before any credential is sent (`macos_session_env_check_cmd`). Credentials are never written to the
  guest's disk: `~/.augur-env` holds only non-secret per-VM env, and augur's other ssh calls carry no
  `SendEnv`. A credential-bearing `~/.augur-env` an older augur wrote loses its credentials at the first
  push, including the push that refuses an old base and the push a running VM still gets when its
  credentials fail to resolve (`resolve_running_macos_vm_credentials`). New closing sentence: on the
  macOS host the values sit in that one `ssh` process's environment for the session's life; macOS is
  **expected** to serve it only to the same user and root, which is not yet observed on a Mac and is
  stated as a residual risk, not an enforced fact. The Container sentence and the `setup-token --macos`
  sentence are unchanged.
- **`**Why:**` (`:184-187`).** Adds the macOS reason: keeping credentials out of `~/.augur-env` keeps
  them off the clone's disk, which `down --macos` persists.
- **`Enforced by` (`:188-204`).** macOS mode now reads: `tests/56_macos_session_credentials.sh`, through
  a recording `ssh_macos` **and an `ssh` shim on PATH**, asserts that the session ssh carries
  `-o SendEnv=` for exactly the resolved names with the values only in its own environment; that no
  value is on any ssh/scp argv, in any guest file (`~/.augur-env` included) or (for file- and
  `gh`-sourced values) in any other ssh call's environment; that build/update write the `AcceptEnv`
  drop-in; and that a guest without it gets no session and no git helper, and has an older augur's
  credential lines removed (also when a later step of that push fails, and when a running VM's
  credentials fail to resolve). Review-only (Mac-only): that a real guest sshd honours the drop-in, the
  guest's process list, and the host-side environment visibility. The Container and `tests/52`
  sentences are unchanged.
- **Summary (`:217-226`).** I10's partial coverage now reads "the macOS session ssh's argv and
  environment" instead of "the macOS `~/.augur-env` push's ssh argv". The review-only remainder is now
  "a real guest sshd honouring the `AcceptEnv` drop-in, a real guest's process list, and the host-side
  environment visibility the Rule relies on".
- **Marks.** `diff <(git show 70c5061:docs/security-reviews/INVARIANTS.md | grep '^#') <(grep '^#'
  docs/security-reviews/INVARIANTS.md)` is empty: every heading line, marks included, is identical. I1–I8

## What the code now does for I10 (at `baccfcd`)

**Resolution is unchanged; its running-VM failure path is new.** `resolve_session_credentials`
(`augur:526`), `validate_secret_value` (`:472`), `resolve_api_key` and `session_credential_env` (`:2920`)
are code-identical to `70c5061` with comments stripped. `session_credential_names` (`:553`) is new: each
`agent_auth_specs` guest variable, then `GH_TOKEN`. On a running VM, `prepare_macos_session` (`:4747`)
and `cmd_up_macos`'s already-running branch (`:4554`, after the self-test at `:4546`) now resolve through
`resolve_running_macos_vm_credentials` (`:4813-4819`). When resolution fails it empties `_creds`, runs
`push_macos_guest_env "$vm" --require-session-env || true` (no credential and no git helper; an old base
is refused there with its remedy), prints a closing error and exits 1. So a bad or unreadable host
credential no longer leaves an older augur's credential-bearing `~/.augur-env` in place. On a boot the
resolve still runs before `augur-vm` is called at all (`:4567`), and the stopped VM is not booted for a
scrub.

**Which ssh carries `SendEnv`.**
- **Only `ssh_macos_session`** (`augur:990-998`), which has exactly two callers: `cmd_claude_macos`'s
  launch (`:4832`) and `cmd_shell_macos`'s (`:4842`). `SendEnv=` appears in one line of non-comment code
  in `augur` (`:993`), which test 56 pins.
- **None on every other ssh.** `ssh_macos` (`:920-924`) is unchanged in behaviour; it is now a thin
  wrapper over `_macos_ssh_cmd` (`:929-961`), which builds the same option array: `-F /dev/null`, `-p
  <gvproxy forward port>`, `StrictHostKeyChecking=accept-new`, the per-VM known-hosts file,
  `LogLevel=ERROR`, `ConnectTimeout=10`, `ServerAliveInterval=15`, `ServerAliveCountMax=4`, the key
  options, then `user@host`. A diff of the old `ssh_macos` against the new `ssh_macos` +
  `_macos_ssh_cmd` (comments stripped) shows only the move into arrays; the option list, its order, and
  the `exit 1` on an unresolvable host/port are the same. `macos_ssh_host` / `macos_ssh_port` (the
  gvproxy forward) are code-identical. No `ControlMaster`/`ControlPath` (comment at `:949`), so the env a
  session sends belongs to its own connection. `scp_to_macos` (`:1000`), `ssh_macos_provision` and
  `ssh_macos_provision_stdin` are code-identical.
- **`setup-token --macos`.** `cmd_setup_token_macos` (`:5013`) is code-identical. Its login ssh is a plain
  `ssh_macos … -t`, so it has no `SendEnv`, and it does not call the resolver.

**How the values reach the ssh process.** `ssh_macos_session` first resolves the ssh command in augur's
shell (`_macos_ssh_cmd`, so the host/port lookups never see a value), builds `-o SendEnv=${_kv%%=*}` for
each `_creds` entry (names only), then in a subshell runs `export "$_kv"` for each entry (a builtin, no
argv) and `exec`s the ssh. Argv carries only `SendEnv=<NAME>` options and the remote command string,
which holds no value. A file- or `gh`-sourced value lives in that one ssh process's environment. The
comment above the function (`:963-989`) now states that this is true only for those sources, and
records as an `Accepted trade-off` that a credential the operator exported into augur's own environment
is inherited by augur and every child anyway (none forwards it).

**What `~/.augur-env` still holds.** `push_macos_guest_env` (`:4214-4275`) writes a header, the
Homebrew `shellenv` eval, the agent's PATH, `DEVELOPER_DIR` and `agent_fixed_env` (`DISABLE_AUTOUPDATER=1`
for Claude), then the end marker. No `_creds` entry is written (test 56 asserts the old credential loop is
gone). It still wires git's credential helper when `creds_have_gh_token` (`:562`), and the helper holds
only the `$GH_TOKEN` reference (`macos_git_credential_helper_cmd`, `:4171`). The atomic write (umask 077
temp file, end-marker check, rename) and the age-based temp cleanup are as recorded on 2026-11-07. The
file is rewritten whole, so the first push to a guest whose file an older augur wrote removes the
credentials from it; the comment at `:4193-4195` records as an `Accepted trade-off` that the old bytes may
remain in the clone's free disk blocks (the old-base remedy deletes the clone). A failed push is **fatal
for a session** too (`prepare_macos_session`, `:4760`): `~/.zshenv` sources the file after sshd has set
the session env, so a stale `export GH_TOKEN=…` would replace the fresh value.

**Exit statuses of the push.** With `--require-session-env` the acceptance check is the first guest
step and sets `_acc=10` on failure (`:4250`). The `~/.augur-env` write exits `1 + _acc` and the
`~/.zshenv` line `4 + _acc`; after both, `[ $_acc = 0 ] || exit 10` (`:4254`), before the git helper
(exit 3, warn only). The host maps 10/11/14 to "refused" plus the step outcome 0/1/4 (`:4260`), prints
the step's warning (for 11 also "it may still hold credentials an older augur wrote"), then the remedy
(`macos_session_env_refused`), and returns 1. So a refusal is never hidden behind a later failing step.
Any other status (255 on a dropped connection) is reported as an unknown outcome.

**The drop-in: install / verify / rollback.** `install_macos_session_env_acceptance` (`:4050-4094`),
called fatally by `cmd_build_macos` (`:3748`, before the final integrity check and save) and
`cmd_update_macos` (`:5691`, on the staging clone, right after it boots and **before** the agent
installer, Homebrew and custom provisioning; the base VM is left as-is on failure).
- Writes `/etc/ssh/sshd_config.d/200-augur-session-env.conf` (`:4023`) holding one line,
  `AcceptEnv ANTHROPIC_API_KEY CLAUDE_CODE_OAUTH_TOKEN GH_TOKEN`. The names are exact (no patterns) and
  are checked against `^[A-Za-z_][A-Za-z0-9_]*$` before they reach the root script (`:4056-4058`).
- The script is staged in the guest user's home over ssh stdin, then run by `sudo -S` with the admin
  password on stdin, so the password is on no argv.
- As root: the candidate is written to `/etc/ssh/augur-session-env.candidate` (root:wheel, 644), and a
  test config (an `Include` of the candidate, then a copy of `/etc/ssh/sshd_config`) is checked with
  **one** `sshd -T -f <test config>` run. `accepts` lowercases the keyword and reads every field, so both
  macOS's `AcceptEnv NAME` and upstream's `acceptenv` forms pass. Exit 2 if it fails (the candidate never
  goes live) (`:4076`).
- Only then `mv -f` into `sshd_config.d` (`:4077`). The live config is checked the same way, and the
  drop-in is removed if that fails (exit 3, `:4078`).
- One fresh `ssh_macos … true` must then succeed (exit 4 otherwise, `:4087-4089`). On any failure,
  sshd's stderr is shown through `sanitize_guest_lines` and the function returns 1. If that fresh
  connection fails, the drop-in stays live; the comment at `:4044-4049` records this as an
  `Accepted trade-off`: only a scratch VM kept with `AUGUR_KEEP_BUILD_VM=1` survives the failure, since
  the build/update never saves it and otherwise deletes it.

**Old bases: refusal and scrub, on one code path.** `macos_session_env_check_cmd` (`:4779-4781`) is
`grep -qxF '<the exact AcceptEnv line>' <drop-in>`, so a base built for different names is refused too.
It runs only inside `push_macos_guest_env … --require-session-env`; no guest command runs it on its own.
- **Boot path.** `cmd_up_macos` calls `require_macos_session_env_accepted` (`:4801-4804`) right after the
  SSH wait (`:4664`), before the clock, the screen-lock settings and the self-test (`:4675`). It is
  `local _creds=(); push_macos_guest_env "$1" --require-session-env || exit 1`: the check and the
  non-secret rewrite in one connection, and with `_creds` emptied no git helper goes to a guest not yet
  self-tested. The boot's second push (`:4713`, after the self-test and the `~/.gitconfig` scp) wires the
  helper without checking again. Any failure stops the boot; the VM is left running. The comment above
  the clock sync (`:4649-4663`) now names exactly these three pre-self-test steps and says none sends an
  agent or gh credential.
- **Running VM.** `cmd_up_macos`'s already-running branch (`:4555`) and `prepare_macos_session`
  (`:4760`) call the same `push_macos_guest_env … --require-session-env`, with the resolved `_creds`; a
  refused guest exits 10 before the helper step, so it gets no git helper and no session ssh.
- No fallback to writing credentials to disk and no in-place patching of project VMs, per ADR-0023.

**What `up --macos` delivers.** No credential: it never calls `ssh_macos_session`. It still resolves and
validates (`:4567` before the clone; `:4554` on the running branch), and the result decides whether the
push wires the git helper. A `claude`/`shell --macos` that boots through `cmd_up_macos` reuses the
caller's `_creds` (`cmd_up_macos` no longer declares its own `local _creds`).

**Container mode — unchanged.** `cmd_claude` (`:3028`) and `cmd_shell` (`:3061`) are code-identical:
they resolve and pass `--env-file <(session_credential_env)` to `eng exec` (`:3053`, `:3076`).
`container run` still gets no credential.

**Accepted trade-offs, as commented in code.**
- Carried: no fresh self-test before a `claude`/`shell --macos` session on a running VM (`:4754`); the
  concurrent-command gaps in `prepare_macos_session` (`:4730`); the duplicate `~/.zshenv` line from two
  racing pushes (`:4241`).
- New on this branch: host-env-sourced credentials are held by augur and its children (`:976`); the
  drop-in is not rolled back when the post-install connection fails (`:4044`); old credential bytes may
  remain in free disk blocks (`:4193`).

## Residual risks

- **Host-side process-env visibility.** For the session's life, the values sit in the host `ssh`
  process's environment. INVARIANTS, ADR-0023 and the `ssh_macos_session` comment now all say macOS is
  **expected** to serve another process's environment only to its own user and root, who can already
  read the host files and `gh` token, and that this is **not yet observed on a Mac** (`ps -E` from a
  second account). Plain `ps` does not print environments.
- **Host-env-sourced credentials are already in augur's environment.** When `ANTHROPIC_API_KEY` /
  `CLAUDE_CODE_OAUTH_TOKEN` come from the operator's environment rather than their host file, augur's
  own process and **every** child (each `ssh_macos`, `augur-vm`, `gh`, …) inherit them anyway. They are
  not forwarded: `ssh_macos` is hermetic and sends no `SendEnv`. ADR-0023 and the `ssh_macos_session`
  comment now claim "only this ssh holds it" for file- and `gh`-sourced values only, and the comment
  (`:976`) records the rest as an `Accepted trade-off`. Test 56 asserts the narrower form.
- **Old credential bytes in free disk blocks.** Rewriting a credential-bearing `~/.augur-env` an older
  augur wrote (or removing an old `~/.augur-env.tmp.*`) frees the blocks without overwriting them, so a
  persisted clone may still hold the old tokens in free space. ADR-0023 records this, and so does the
  `push_macos_guest_env` comment (`:4193`, `Accepted trade-off`). The remedy for old bases,
  `destroy --macos && up --macos`, deletes the clone.
- **Depends on the guest git helper chain reset (not on this branch).** git's credential helper chain
  in the guest is never reset here. After a successful push, git's `store` step hands `GH_TOKEN` to every
  configured helper, including the system or host `osxkeychain` helper, which can write it into the
  guest's login keychain **on disk** if that keychain is unlocked. "Nothing on the guest disk" relies on
  that chain being reset, which branch `fix/macos-git-helper-reset` does; it is planned to merge
  **before** this branch. ADR-0023 records the dependency ("Depends on"). Until it lands, the guest's
  keychain is a path from a session's `GH_TOKEN` to the guest's disk. This branch does not duplicate the
  fix.
- **Pre-self-test guest interaction on the boot path.** Every boot now runs one
  `push_macos_guest_env --require-session-env` before the self-test, with `_creds` emptied: the check, the
  non-secret `~/.augur-env` and the `~/.zshenv` line, and no git helper. The clock fix and
  `configure_macos_guest_session` follow, both before the self-test as on `70c5061`. None of them sends an
  agent or gh credential (the clock and screen-lock steps feed `sudo -S` the guest's own admin password,
  as before), so I1's "no credential to an unproven guest" holds. The comment above them (`:4649-4663`)
  names exactly these three steps.
- **A post-install probe failure leaves the drop-in live.** If the fresh connection after the drop-in
  install fails, nothing rolls it back. Only a scratch VM kept with `AUGUR_KEEP_BUILD_VM=1` survives that
  failure; no base VM is saved. Recorded as an `Accepted trade-off` (`:4044`) and in ADR-0023.
- **An old base still needs a successful update.** `update --macos` now installs the drop-in before any
  network step, but the update still saves the base VM only after every step (Homebrew, provisioning, the
  signature check) passed. While a Homebrew upgrade or a download keeps failing, an old base stays without
  the drop-in and its clones keep being refused; a full `build --macos` needs the network too.
- **A guest that lies to the acceptance check** gains nothing (ADR-0023, comment above
  `macos_session_env_check_cmd`): its own sshd decides what it accepts, and the worst case is a session
  without credentials.
- Carried unchanged: the reuse-path self-test spoofing caveat (item 46's project-VM half in 2026-11-05),
  and the macOS admin password exclusion in I10's Note.

## macOS 27 guest facts the design relies on

**Observed** (ADR-0023, on a clone of the base VM, 2026-11-07; not re-observed here, since this host has
no Mac):
- `/etc/ssh/sshd_config` has `Include /etc/ssh/sshd_config.d/*` (absolute, near the top), and
  `sshd_config.d` holds only macOS's own `100-macos.conf` (root:wheel, 644).
- `sudo sshd -T` prints `AcceptEnv LANG` and `AcceptEnv LC_*`: mixed-case keyword, one name per line.
  `5ba0a2a` makes test 56's sshd shim print this form by default (`SSHD_LOWER=1` selects upstream's
  lowercase), and the install's `awk 'tolower($1) == "acceptenv"'` accepts both.
- `launchctl print system/com.openssh.sshd` shows a LaunchDaemon with `active count = 0` while a session
  is open, consistent with one sshd per connection. That is why the candidate is verified before it goes
  live.

**Still Mac-only and unobserved:**
- that macOS serves another user's process environment only to that user and root;
- that `sshd -T -f <test config>` follows the staged config's absolute `Include` as described;
- end-to-end delivery: the `SendEnv` values present in a `claude`/`shell --macos` session, and absent from
  a plain `ssh`;
- a real guest's process list during a session;
- the BSD-userland behaviour of the push (`find -mmin`, `umask`, `mv`) and of the root script
  (`mktemp`, `grep -qxF`, `awk`), which test 56 exercised with GNU tools.

## Contract vs code

No divergence on I10's argv property: the only credential-bearing ssh puts names, never values, on argv,
and test 56 enforces it through a real `ssh` shim. The three wording divergences recorded at `5ba0a2a`
are fixed at `baccfcd`:
- INVARIANTS no longer states the host-side environment visibility as fact (it matches ADR-0023's "not
  yet observed");
- ADR-0023 and the `ssh_macos_session` comment narrow "no other process holds the values" to file- and
  `gh`-sourced credentials, with an `Accepted trade-off` for env-var-sourced ones;
- INVARIANTS mentions the scrub of a refused guest's `~/.augur-env`.

One dependency, not a divergence in this branch's code: INVARIANTS' "never written to the guest's disk"
for `GH_TOKEN` holds only once git's helper chain in the guest is reset (`fix/macos-git-helper-reset`,
planned to merge first); see Residual risks.
