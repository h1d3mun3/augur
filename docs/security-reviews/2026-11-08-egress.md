- **`**Rule:**` (`INVARIANTS.md:161-186`).** Before: on macOS the credentials are written to
  `~/.augur-env` via SSH stdin by `push_macos_guest_env` on every `up` / `claude` / `shell --macos`. Now:
  in macOS VM mode they reach the guest **only as the environment of the interactive ssh** that starts
  `augur claude --macos` / `augur shell --macos` (`ssh_macos_session`). A subshell `export`s the values
  and execs that one `ssh`, which names exactly the resolved variables with `-o SendEnv=<NAME>` (never
  `-o SetEnv=NAME=value`). The guest's sshd accepts exactly those names through a root-owned drop-in that
  the base VM build/update writes (`install_macos_session_env_acceptance`). A guest without it is refused
  before any credential is sent (`macos_session_env_check_cmd`). Credentials are never written to the
  guest's disk: `~/.augur-env` holds only non-secret per-VM env (git's `GIT_CONFIG_*` helper among it,
  carrying only the `$GH_TOKEN` reference), and augur's other ssh calls carry no `SendEnv`. The
  helper's first entry resets git's helper chain (`git_credential_env`), so git hands `GH_TOKEN` to no
  other helper's `store`, such as `osxkeychain`. A credential-bearing `~/.augur-env` an older augur wrote loses its credentials at the first
  push, including the push that refuses an old base and the push a running VM still gets when its
  credentials fail to resolve (`resolve_running_macos_vm_credentials`). New closing sentence: on the
  macOS host the values sit in that one `ssh` process's environment for the session's life; macOS is
  **expected** to serve it only to the same user and root, which is not yet observed on a Mac and is
  stated as a residual risk, not an enforced fact. The Container sentence and the `setup-token --macos`
  sentence are unchanged.
- **`**Why:**` (`:187-190`).** Adds the macOS reason: keeping credentials out of `~/.augur-env` keeps
  them off the clone's disk, which `down --macos` persists.
- **`Enforced by` (`:191-209`).** macOS mode now reads: `tests/56_macos_session_credentials.sh`, through
  a recording `ssh_macos` **and an `ssh` shim on PATH**, asserts that the session ssh carries
  `-o SendEnv=` for exactly the resolved names with the values only in its own environment; that no
  value is on any ssh/scp argv, in any guest file (`~/.augur-env` included) or (for file- and
  `gh`-sourced values) in any other ssh call's environment; that build/update write the `AcceptEnv`
  drop-in; that the `GIT_CONFIG_*` lines in `~/.augur-env` hold no token value; and that a guest without
  the drop-in gets no session (on a boot, no `GIT_CONFIG_*` lines either) and has an older augur's
  credential lines removed (also when a later step of that push fails, and when a running VM's
  credentials fail to resolve). Review-only (Mac-only): that a real guest sshd honours the drop-in, the
  guest's process list, and the host-side environment visibility. `tests/35_macos_gitconfig_helper.sh`
  is added for the reset (real `git credential fill/approve`, no other configured helper called). The
  Container and `tests/52` sentences are unchanged.
- **Summary (`:222-231`).** I10's partial coverage now reads "the macOS session ssh's argv and
  environment" instead of "the macOS `~/.augur-env` push's ssh argv". The review-only remainder is now
  "a real guest sshd honouring the `AcceptEnv` drop-in, a real guest's process list, and the host-side
  environment visibility the Rule relies on".
- **This update (for `1b67a58`).** I10's `**Rule:**` adds the runtime delivery check
  (`macos_session_env_delivery_cmd`, exit 197, read as the refusal only when a credential was sent)
  and moves git's `GIT_CONFIG_*` helper out of `~/.augur-env` into the session's remote command
  (`macos_session_git_env_cmd`, only when `GH_TOKEN` is sent); `~/.augur-env` "never reads the

## What the code now does for I10 (at `4a9b970`, with the changes at `1b67a58`)

**At `1b67a58` (the third review's fixes).** Where the passages below differ, this paragraph wins:
- **A running VM is attached to only after a self-test of its current boot.** `prepare_macos_session`
  calls `require_macos_egress_verified` right after `require_macos_egress_mode_current`, before any
  guest step (no push, no resolve). It exits 1, leaving the VM running, unless
  `macos_egress_verified_file` (`<slug>-<hash>.egress-verified` in the proxy directory) holds the VM's
  current run id (`macos_vm_run_id`: augur-vm's `run.pid`). `cmd_up_macos` removes the record just
  before `augur-vm run` and writes it (`macos_record_egress_verified`) right after
  `verify_macos_egress_locked` returns, on the boot path and on the already-running branch;
  `stop_unverified_macos_vm`, `down` and `destroy` remove it. With no run id `up` writes nothing and
  warns, so sessions refuse. Egress-off: not written and not checked (a `--no-egress` session attaches
  only to a VM booted that way). So an `up --macos` interrupted between `augur-vm run` and the
  self-test no longer leaves a VM that the next `claude`/`shell --macos` sends credentials to.
- **git's helper is per session, not in `~/.augur-env`.** `push_macos_guest_env` no longer calls
  `git_credential_env` or reads `_creds` at all; the `GH_TOKEN` guard and the `_creds` emptying in
  `require_macos_session_env_accepted` / `resolve_running_macos_vm_credentials` are gone.
  `ssh_macos_session` builds the remote command as the delivery check, then
  `macos_session_git_env_cmd` (each `git_credential_env` line through `macos_env_add_export`, joined
  as `export NAME='value'; `, empty without a gh token in `_creds`), then the caller's command. The
  values hold only the `$GH_TOKEN` reference (test 56 asserts no value on any argv). A rewrite of
  `~/.augur-env` drops `GIT_CONFIG_*` lines a `4a9b970` push wrote, on every path that pushes.
- **Exit 197** is mapped to the delivery refusal only when the delivery check is non-empty, i.e. a
  credential was sent.
- **Temp cleanup.** Every push, checked or not, runs
  `find … -name '.augur-env.tmp.*' ! -name .augur-env.tmp.$$ \( -mmin +1 -o -newer "$_now" \)`, with
  `_now` a reference file from `mktemp /tmp/augur-env-now.XXXXXX` removed right after. A concurrent
  push's fresh file survives; one dated ahead of the guest clock goes.
- **One teardown.** `stop_unverified_macos_boot` is renamed `stop_unverified_macos_vm`; it also removes
  the record, and `verify_macos_egress_locked`'s failure branch now calls it instead of inlining
  `"$VM_CLI" stop` / `stop_gvproxy` / `stop_proxy`. `require_macos_session_env_accepted`'s message no
  longer says "before its egress self-test".
- **`valid_env_name`** replaces the three copies of `^[A-Za-z_][A-Za-z0-9_]*$` (`macos_env_add_export`,
  `macos_session_env_delivery_cmd`, `install_macos_session_env_acceptance`).

**Resolution is unchanged; its running-VM failure path is new.** `resolve_session_credentials`
(`augur:526`), `validate_secret_value` (`:472`), `resolve_api_key` and `session_credential_env` (`:2999`)
are code-identical to `c9068b2` (and to `70c5061`) with comments stripped.
`session_credential_names` (`:553`) is new: each `agent_auth_specs` guest variable, then `GH_TOKEN`. On a running VM, `prepare_macos_session` (`:4814`)
and `cmd_up_macos`'s already-running branch (`:4623`, after the self-test at `:4615`) now resolve through
`resolve_running_macos_vm_credentials` (`:4893-4899`). When resolution fails it empties `_creds`, runs
`push_macos_guest_env "$vm" --require-session-env || true` (no credential, and so no `GIT_CONFIG_*`
helper lines; an old base is refused there with its remedy), prints a closing error and exits 1 (at `1b67a58` without emptying `_creds`: the push reads none). So a bad or unreadable host
credential no longer leaves an older augur's credential-bearing `~/.augur-env` in place. On a boot the
resolve still runs before `augur-vm` is called at all (`:4636`), and the stopped VM is not booted for a
scrub. Why such an emptied-`_creds` push is safe before any self-test is explained once, in the
`push_macos_guest_env` header (`:4249-4252`); the other sites point there.

**Which ssh carries `SendEnv`.**
- **Only `ssh_macos_session`** (`augur:1046-1061`), which has exactly two callers: `cmd_claude_macos`'s
  launch (`:4912`) and `cmd_shell_macos`'s (`:4922`). `SendEnv=` appears in one line of non-comment code
  in `augur` (`:1051`), which test 56 pins.
- **None on every other ssh.** `ssh_macos` (`:968-972`) is unchanged in behaviour; it is now a thin
  wrapper over `_macos_ssh_cmd` (`:977-1009`), which builds the same option array: `-F /dev/null`, `-p
  <gvproxy forward port>`, `StrictHostKeyChecking=accept-new`, the per-VM known-hosts file,
  `LogLevel=ERROR`, `ConnectTimeout=10`, `ServerAliveInterval=15`, `ServerAliveCountMax=4`, the key
  options, then `user@host`. A diff of the old `ssh_macos` against the new `ssh_macos` +
  `_macos_ssh_cmd` (comments stripped) shows only the move into arrays; the option list, its order, and
  the `exit 1` on an unresolvable host/port are the same. `macos_ssh_host` / `macos_ssh_port` (the
  gvproxy forward) are code-identical. No `ControlMaster`/`ControlPath` (comment at `:997`), so the env a
  session sends belongs to its own connection. `scp_to_macos` (`:1079`), `ssh_macos_provision` and
  `ssh_macos_provision_stdin` are code-identical.
- **`setup-token --macos`.** `cmd_setup_token_macos` (`:5095`) is code-identical. Its login ssh is a plain
  `ssh_macos … -t`, so it has no `SendEnv`, and it does not call the resolver.

**How the values reach the ssh process.** `ssh_macos_session` first builds the remote command
(`macos_session_env_delivery_cmd` in front of the caller's last argument, below), then resolves the ssh
command in augur's shell (`_macos_ssh_cmd`, so the host/port lookups never see a value), builds
`-o SendEnv=${_kv%%=*}` for each `_creds` entry (names only), then in a subshell runs `export "$_kv"` for
each entry (a builtin, no argv) and `exec`s the ssh. Argv carries only `SendEnv=<NAME>` options and the
remote command string, which holds names and no value. A file- or `gh`-sourced value lives in that one
ssh process's environment. The comment above the function (`:1011-1045`) states that this is true only
for those sources, and records as an `Accepted trade-off` (`:1024`) that a credential the operator
exported into augur's own environment is inherited by augur and every child anyway (none forwards it).

**Delivery is checked in the guest (new at `4a9b970`).** `macos_session_env_delivery_cmd`
(`:1070-1077`) prints, for each `_creds` name, `[ -n "${NAME:-}" ] || exit 197; `
(`MACOS_SESSION_ENV_MISSING_RC`, `:1064`). Names are checked against `^[A-Za-z_][A-Za-z0-9_]*$` first;
nothing is printed for an empty `_creds`. The guest runs it before `zsh -l -c …` / `exec zsh -l`, so a
credential that sshd dropped (a guest `sshd_config` that lost its `Include`, which the drop-in grep
cannot see) stops the session before the agent or shell starts, and no value is printed in the guest.
`ssh_macos_session` maps status 197 to `macos_session_env_refused "$vm" delivery` (`:4853-4867`) and
returns 1; any other status passes through. Comment at `:1030-1036`, with the `Accepted trade-off` that
an agent or shell that itself exits 197 is reported as this refusal. At `1b67a58` the mapping applies only
when the check was sent (a credential was sent); otherwise 197 passes through like any status.

**What `~/.augur-env` still holds** (at `1b67a58` without the git helper lines, the guard and the
checked-push-only cleanup; see the top of this section). `push_macos_guest_env` (`:4266-4335`) writes a header, the
Homebrew `shellenv` eval, the agent's PATH, `DEVELOPER_DIR`, `agent_fixed_env` (`DISABLE_AUTOUPDATER=1`
for Claude) and, when `creds_have_gh_token` (`:562`), git's helper lines from `git_credential_env`
(`:606-614`), then the end marker. Every line goes through `macos_env_add_export` (`:4211-4219`), as on
`c9068b2`. No `_creds` entry is written (test 56 asserts no credential value in the file; test 35's
source guard counts exactly two `macos_env_add_export` loops, the fixed env and the git helper). The
helper lines are `GIT_CONFIG_COUNT=2`, an empty `credential.https://github.com.helper` (the reset), then
augur's helper, which holds only the `$GH_TOKEN` reference; the token itself arrives with the session
ssh, and the helper's shell expands it when git calls it. **New at `4a9b970`:** the validated helper
lines are collected into a block of their own and wrapped in `if [ -n "${GH_TOKEN:-}" ]; then … fi`
(`:4279-4286`; explained at `:4242-4247`). So the reset and helper apply only in a guest shell that has
a token, i.e. an augur session's, where sshd sets `GH_TOKEN` before `~/.zshenv` sources the file. The
VM's GUI Terminal, a hand-run `ssh`, and a session started without a host gh token keep git's own
helpers instead of a cleared chain plus a helper answering `password=` (HTTPS git failing with 401 and
no prompt). The atomic write (umask 077 temp file, end-marker check, rename) is as recorded on
2026-11-07. The temp cleanup (`:4308-4314`): a plain push removes `~/.augur-env.tmp.*` older than a
minute; **new at `4a9b970`**, the push that carries the acceptance check removes every one except its
own (`! -name .augur-env.tmp.$$`), with no age filter, because a refused guest gets no later push and
a guest clock that lags right after a boot makes an old file look new (comment `:4291-4297`, with the
`Accepted trade-off` that a concurrent push loses its temp file and fails). The file is rewritten whole,
so the first push to a guest whose file an older augur wrote removes the credentials from it; the
comment at `:4234-4236` records as an `Accepted trade-off` that the old bytes may remain in the clone's
free disk blocks (the old-base remedy deletes the clone). A failed push is **fatal for a session** too
(`prepare_macos_session`, `:4827`): `~/.zshenv` sources the file after sshd has set the session env, so
a stale `export GH_TOKEN=…` would replace the fresh value.

**Exit statuses of the push.** With `--require-session-env` the acceptance check is the first guest
step and sets `_acc=10` on failure (`:4311`). The `~/.augur-env` write exits `1 + _acc` and the
`~/.zshenv` line `4 + _acc`; after both, `[ $_acc = 0 ] || exit 10` (`:4317`) is the last guest step.
The push has no exit 3: #277 removed the guest-side helper write and its warn-only path, so the
remaining statuses are 0, 1, 4 and, with a refusal, 10, 11, 14. The host maps 10/11/14 to "refused" plus the step outcome 0/1/4 (`:4322`), prints
the step's warning (for 11 also "it may still hold credentials an older augur wrote"), then the remedy
(`macos_session_env_refused`), and returns 1. So a refusal is never hidden behind a later failing step.
Any other status (255 on a dropped connection) is reported as an unknown outcome.

**The drop-in: install / verify / rollback.** `install_macos_session_env_acceptance` (`:4121-4165`),
called fatally by `cmd_build_macos` (`:3819`, before the final integrity check and save) and
`cmd_update_macos` (`:5773`, on the staging clone, right after it boots and **before** the agent
installer, Homebrew and custom provisioning; the base VM is left as-is on failure).
- Writes `/etc/ssh/sshd_config.d/200-augur-session-env.conf` (`:4094`) holding one line,
  `AcceptEnv ANTHROPIC_API_KEY CLAUDE_CODE_OAUTH_TOKEN GH_TOKEN`. The names are exact (no patterns) and
  are checked against `^[A-Za-z_][A-Za-z0-9_]*$` before they reach the root script (`:4127-4129`).
- The script is staged in the guest user's home over ssh stdin, then run by `sudo -S` with the admin
  password on stdin, so the password is on no argv.
- As root: the candidate is written to `/etc/ssh/augur-session-env.candidate` (root:wheel, 644), and a
  test config (an `Include` of the candidate, then a copy of `/etc/ssh/sshd_config`) is checked with
  **one** `sshd -T -f <test config>` run. `accepts` lowercases the keyword and reads every field, so both
  macOS's `AcceptEnv NAME` and upstream's `acceptenv` forms pass. Exit 2 if it fails (the candidate never
  goes live) (`:4147`).
- Only then `mv -f` into `sshd_config.d` (`:4148`). The live config is checked the same way, and the
  drop-in is removed if that fails (exit 3, `:4149`).
- One fresh `ssh_macos … true` must then succeed (exit 4 otherwise, `:4158-4160`). On any failure,
  sshd's stderr is shown through `sanitize_guest_lines` and the function returns 1. If that fresh
  connection fails, the drop-in stays live; the comment at `:4115-4120` records this as an
  `Accepted trade-off`: only a scratch VM kept with `AUGUR_KEEP_BUILD_VM=1` survives the failure, since
  the build/update never saves it and otherwise deletes it.

**Old bases: refusal and scrub, on one code path.** `macos_session_env_check_cmd` (`:4846-4848`) is
`grep -qxF '<the exact AcceptEnv line>' <drop-in>`, so a base built for different names is refused too.
It runs only inside `push_macos_guest_env … --require-session-env`; no guest command runs it on its own.
- **Boot path.** `cmd_up_macos` calls `require_macos_session_env_accepted` (`:4879-4885`, call at
  `:4733`) right after the SSH wait (`:4716`), before the clock, the screen-lock settings and the
  self-test (`:4744`). It runs `push_macos_guest_env "$1" --require-session-env` with a local empty
  `_creds`: the check and the non-secret rewrite in one connection, and with `_creds` emptied
  `git_credential_env` prints nothing, so a guest not yet self-tested gets no `GIT_CONFIG_*` lines. The
  boot's second push (`:4780`, after the self-test and the `~/.gitconfig` scp) writes them without
  checking again. **New at `4a9b970`:** any failure of that first push (a refusal, a transport error, a
  full disk) prints "Stopping VM … (its clone is kept)" and calls `stop_unverified_macos_boot`
  (`:4553-4557`: `"$VM_CLI" stop`, `stop_gvproxy`, `stop_proxy`), then exits 1. The SSH-wait timeout
  (`macos_boot_ssh_failed`, `:4521`) uses the same function. Before, the VM was left running with its
  containment never checked, and the next `claude`/`shell --macos` would take `prepare_macos_session`'s
  running path and send credentials to it with no self-test. The comment above the clock sync
  (`:4718-4732`) names exactly these three pre-self-test steps and says none sends an agent or gh
  credential. At `1b67a58` that push writes no git helper either way (no `_creds` emptying), the
  function is `stop_unverified_macos_vm`, and the message reads "its boot cannot go on".
- **Running VM.** `cmd_up_macos`'s already-running branch (`:4624`) and `prepare_macos_session`
  (`:4827`) call the same `push_macos_guest_env … --require-session-env`, with the resolved `_creds`; a
  refused guest gets no session ssh, so no credential. Its new `~/.augur-env` does carry the
  `GIT_CONFIG_*` lines when the host has a gh token (they are built host-side before the guest
  answers the check); they hold no secret, and since `4a9b970` they apply only in a shell with
  `GH_TOKEN`. At `1b67a58` no push writes them: the session exports them. `prepare_macos_session`
  also requires the passed-self-test record before any of this.
- **The remedy** (`macos_session_env_refused`, `:4853-4867`) now says that
  `augur destroy --macos && augur up --macos` is enough when the base VM is already up to date, and to
  run `augur update --macos` first otherwise. augur does not detect the base's version.
- No fallback to writing credentials to disk and no in-place patching of project VMs, per ADR-0023.

**What `up --macos` delivers.** No credential: it never calls `ssh_macos_session`. It still resolves and
validates (`:4636` before the clone; `:4623` on the running branch); at `4a9b970` the result decided whether the
push wrote the `GIT_CONFIG_*` helper lines (at `1b67a58` no push does). A `claude`/`shell --macos` that boots through `cmd_up_macos` reuses the
caller's `_creds` (`cmd_up_macos` no longer declares its own `local _creds`).

**Container mode — unchanged.** `cmd_claude` (`:3099`) and `cmd_shell` (`:3132`) are code-identical:
they resolve and pass `--env-file <(session_credential_env)` to `eng exec` (`:3124`, `:3147`).
`container run` still gets no credential.

**Accepted trade-offs, as commented in code.**
- Carried: no fresh self-test before a `claude`/`shell --macos` session on a running VM (`:4821`; at
  `1b67a58` only on a VM whose current boot passed one); the
  concurrent-command gaps in `prepare_macos_session` (`:4797`); the duplicate `~/.zshenv` line from two
  racing pushes (`:4304`).
- New on this branch: host-env-sourced credentials are held by augur and its children (`:1024`); the
  drop-in is not rolled back when the post-install connection fails (`:4115`); old credential bytes may
  remain in free disk blocks (`:4234`); an agent or shell exiting 197 is reported as the delivery
  refusal (`:1035`; at `1b67a58` only after a credential was sent); a concurrent push loses its temp file
  to a checked push's cleanup (`:4296`; at `1b67a58` only one created in the instant between another
  push's reference file and its `find`). New at `1b67a58`: a `GIT_CONFIG_*` set a guest startup file exports
  replaces augur's in the session (`git_credential_env`'s comment).

## Residual risks

- **Host-side process-env visibility.** For the session's life, the values sit in the host `ssh`
  process's environment. INVARIANTS, ADR-0023 and the `ssh_macos_session` comment now all say macOS is
  **expected** to serve another process's environment only to its own user and root, who can already
  read the host files and `gh` token, and that this is **not yet observed on a Mac** (`ps -E` from a
  second account). Plain `ps` does not print environments.
- **Host-env-sourced credentials are already in augur's environment.** When `ANTHROPIC_API_KEY` /
  `CLAUDE_CODE_OAUTH_TOKEN` come from the operator's environment rather than their host file, augur's
  own process and **every** child (each `ssh_macos`, `augur-vm`, `gh`, …) inherit them anyway. They are
  not forwarded: `ssh_macos` is hermetic and sends no `SendEnv`. ADR-0023 and the `ssh_macos_session`
  comment now claim "only this ssh holds it" for file- and `gh`-sourced values only, and the comment
  (`:1024`) records the rest as an `Accepted trade-off`. Test 56 asserts the narrower form.
- **Old credential bytes in free disk blocks.** Rewriting a credential-bearing `~/.augur-env` an older
  augur wrote (or removing an old `~/.augur-env.tmp.*`) frees the blocks without overwriting them, so a
  persisted clone may still hold the old tokens in free space. ADR-0023 records this, and so does the
  `push_macos_guest_env` comment (`:4234`, `Accepted trade-off`). The remedy for old bases,
  `destroy --macos && up --macos`, deletes the clone.
- **Relies on the helper-chain reset in `git_credential_env` (on `main` since #277).** After a
  successful push, git's `store` step hands the credential to every configured helper, including the
  system or host `osxkeychain` helper, which can write it into the guest's login keychain **on disk** if
  that keychain is unlocked. "Nothing on the guest disk" holds for `GH_TOKEN` because the first
  `GIT_CONFIG_*` entry (in `~/.augur-env` at `4a9b970`; at `1b67a58` the first export of the session's
  remote command) is an empty `credential.https://github.com.helper`, which clears every helper
  collected from the config files before augur's. ADR-0023 records this ("Depends on").
  Test 35 pins it against real git with `GH_TOKEN` set as the session ssh sets it, and that a guest
  shell augur did not open gets none of the `GIT_CONFIG_*` set and git asks its own helpers there (at
  `4a9b970` through the guard; at `1b67a58` because no file holds the set, even for a shell with a
  `GH_TOKEN` of its own). Residual: at `1b67a58` the exports run in sshd's shell, before the login zsh
  the remote command starts reads its startup files, so a `GIT_CONFIG_*` set any guest startup file
  exports (`/etc/zshenv`, `~/.zshenv`, `~/.zprofile`, `~/.zshrc`) replaces augur's, reset included
  (`Accepted trade-off` at `git_credential_env`; test 35 pins it), and `git -c credential.helper=…` on
  a command line is read after it. Both are in the guest's own hands. Outside augur's sessions the
  guest's own helpers (Apple git's `osxkeychain` included) run as without augur; no augur credential
  is there to hand them.
- **Pre-self-test guest interaction on the boot path.** Every boot now runs one
  `push_macos_guest_env --require-session-env` before the self-test (at `4a9b970` with `_creds` emptied;
  at `1b67a58` the push reads no `_creds`): the check, the
  non-secret `~/.augur-env` (no `GIT_CONFIG_*` lines) and the `~/.zshenv` line. The clock fix and
  `configure_macos_guest_session` follow, both before the self-test as on `c9068b2`. None of them sends an
  agent or gh credential (the clock and screen-lock steps feed `sudo -S` the guest's own admin password,
  as before), so I1's "no credential to an unproven guest" holds. The comment above them (`:4718-4732`)
  names exactly these three steps. Since `4a9b970` a failure of the first one stops the VM, so no
  un-self-tested VM is left for a later session to attach to; the clock and screen-lock steps are
  best-effort and never exit.
- **An interrupted boot (closed at `1b67a58`).** At `4a9b970`, an `up --macos` killed between
  `augur-vm run` and the self-test (Ctrl-C, a kill, a host crash) left a running VM that the next
  `claude`/`shell --macos` attached to and sent credentials, with no self-test. At `1b67a58` the session
  refuses unless the passed-self-test record matches the VM's current run id. It rests on
  `augur-vm run` keeping one pid in `run.pid` for the boot (it writes `getpid()` once and removes the
  file on exit, `RunSession.swift`), which is not observed on a Mac. A guest cannot forge the record:
  it is a host file.
- **The delivery check's exit status is not unique.** An agent or shell that itself exits 197 after a
  credential was sent is reported as "sshd did not accept augur's session credentials" (`Accepted
  trade-off`, `:1035`; at `1b67a58` a session that sent nothing passes 197 through). That costs a
  misleading message after the session ended, never a credential.
- **A push can remove a concurrent push's temp file.** At `4a9b970` any checked push did; at `1b67a58`
  only one created in the instant between another push's `mktemp` reference file and its `find`. The
  concurrent push's `mv` then fails and it reports a failed write (`Accepted trade-off`, in
  `push_macos_guest_env`); augur does not support two commands on the same project at once anyway.
- **A post-install probe failure leaves the drop-in live.** If the fresh connection after the drop-in
  install fails, nothing rolls it back. Only a scratch VM kept with `AUGUR_KEEP_BUILD_VM=1` survives that
  failure; no base VM is saved. Recorded as an `Accepted trade-off` (`:4115`) and in ADR-0023.
- **An old base still needs a successful update.** `update --macos` now installs the drop-in before any
  network step, but the update still saves the base VM only after every step (Homebrew, provisioning, the
  signature check) passed. While a Homebrew upgrade or a download keeps failing, an old base stays without
  the drop-in and its clones keep being refused; a full `build --macos` needs the network too.
- **A guest that lies to the acceptance check** gains nothing (ADR-0023, comment above
  `macos_session_env_check_cmd`): its own sshd decides what it accepts, and the worst case is a session
  without credentials.
- Carried unchanged: the reuse-path self-test spoofing caveat (item 46's project-VM half in 2026-11-05),
  and the macOS admin password exclusion in I10's Note.

## macOS 27 guest facts the design relies on

**Observed** (ADR-0023, on a clone of the base VM, 2026-11-07; not re-observed here, since this host has
no Mac):
- `/etc/ssh/sshd_config` has `Include /etc/ssh/sshd_config.d/*` (absolute, near the top), and

  lowercase), and the install's `awk 'tolower($1) == "acceptenv"'` accepts both.
- `launchctl print system/com.openssh.sshd` shows a LaunchDaemon with `active count = 0` while a session
  is open, consistent with one sshd per connection. That is why the candidate is verified before it goes
  live.

- that `sshd -T -f <test config>` follows the staged config's absolute `Include` as described;

## Contract vs code

No divergence on I10's argv property: the only credential-bearing ssh puts names, never values, on argv,
and test 56 enforces it through a real `ssh` shim. The three wording divergences recorded at `5ba0a2a`
are fixed at `baccfcd`:
- INVARIANTS no longer states the host-side environment visibility as fact (it matches ADR-0023's "not
  yet observed");
- ADR-0023 and the `ssh_macos_session` comment narrow "no other process holds the values" to file- and
  `gh`-sourced credentials, with an `Accepted trade-off` for env-var-sourced ones;
- INVARIANTS mentions the scrub of a refused guest's `~/.augur-env`.

INVARIANTS' "never written to the guest's disk" for `GH_TOKEN` relies on the helper-chain reset in
`git_credential_env`, which `main` has since #277; at `baccfcd` that was an open dependency. I10 now
names the reset and lists test 35 for it; see Residual risks.

## I10's mark

**Stays 🟡 partial.** The macOS argv half and the "values only in the session ssh's environment" half are
now test-enforced (test 56's `ssh` shim and recording `ssh_macos`), alongside Container mode and
`setup-token --macos`. Three parts are still review-only:
- that a real guest sshd honours the drop-in end to end (since `4a9b970` a session whose guest lacks a value it sent
  is refused at run time, so a failure shows as a refusal rather than an unauthenticated agent; I10 says
  so since this update);
- a real guest's process list;
- the host-side environment visibility the Rule relies on.

None of them runs anywhere in CI, and the live tiers (`21`, `22`, `30` live, `e2e_macos_vm.sh`) did not
run here.
