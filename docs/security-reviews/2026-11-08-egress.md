## What changed in the contract

`git log c9068b2..1f192cc -- docs/security-reviews/INVARIANTS.md` lists `d1e7b97`, `7bc96de`, `8dca798`
and `1f192cc`; the net diff is confined to I10 and the closing summary (this update adds one sentence to
I1's `Enforced by`, below). `git diff --stat 70c5061..c9068b2 --

- **`**Rule:**` (`INVARIANTS.md:161-186`).** Before: on macOS the credentials are written to
  `~/.augur-env` via SSH stdin by `push_macos_guest_env` on every `up` / `claude` / `shell --macos`. Now:
  in macOS VM mode they reach the guest **only as the environment of the interactive ssh** that starts
  `augur claude --macos` / `augur shell --macos` (`ssh_macos_session`). A subshell `export`s the values
  and execs that one `ssh`, which names exactly the resolved variables with `-o SendEnv=<NAME>` (never
  `-o SetEnv=NAME=value`). The guest's sshd accepts exactly those names through a root-owned drop-in that
  the base VM build/update writes (`install_macos_session_env_acceptance`). A guest without it is refused
  before any credential is sent (`macos_session_env_check_cmd`). Credentials are never written to the
  guest's disk: `~/.augur-env` holds only non-secret per-VM env (git's `GIT_CONFIG_*` helper among it,
  carrying only the `$GH_TOKEN` reference), and augur's other ssh calls carry no `SendEnv`. The
  helper's first entry resets git's helper chain (`git_credential_env`), so git hands `GH_TOKEN` to no
  other helper's `store`, such as `osxkeychain`. A credential-bearing `~/.augur-env` an older augur wrote loses its credentials at the first
  push, including the push that refuses an old base and the push a running VM still gets when its
  credentials fail to resolve (`resolve_running_macos_vm_credentials`). New closing sentence: on the
  macOS host the values sit in that one `ssh` process's environment for the session's life; macOS is
  **expected** to serve it only to the same user and root, which is not yet observed on a Mac and is
  stated as a residual risk, not an enforced fact. The Container sentence and the `setup-token --macos`
  sentence are unchanged.
- **`**Why:**` (`:187-190`).** Adds the macOS reason: keeping credentials out of `~/.augur-env` keeps
  them off the clone's disk, which `down --macos` persists.
- **`Enforced by` (`:191-209`).** macOS mode now reads: `tests/56_macos_session_credentials.sh`, through
  a recording `ssh_macos` **and an `ssh` shim on PATH**, asserts that the session ssh carries
  `-o SendEnv=` for exactly the resolved names with the values only in its own environment; that no
  value is on any ssh/scp argv, in any guest file (`~/.augur-env` included) or (for file- and
  `gh`-sourced values) in any other ssh call's environment; that build/update write the `AcceptEnv`
  drop-in; that the `GIT_CONFIG_*` lines in `~/.augur-env` hold no token value; and that a guest without
  the drop-in gets no session (on a boot, no `GIT_CONFIG_*` lines either) and has an older augur's
  credential lines removed (also when a later step of that push fails, and when a running VM's
  credentials fail to resolve). Review-only (Mac-only): that a real guest sshd honours the drop-in, the
  guest's process list, and the host-side environment visibility. `tests/35_macos_gitconfig_helper.sh`
  is added for the reset (real `git credential fill/approve`, no other configured helper called). The
  Container and `tests/52` sentences are unchanged.
- **Summary (`:222-231`).** I10's partial coverage now reads "the macOS session ssh's argv and
  environment" instead of "the macOS `~/.augur-env` push's ssh argv". The review-only remainder is now
  "a real guest sshd honouring the `AcceptEnv` drop-in, a real guest's process list, and the host-side
  environment visibility the Rule relies on".
- **This update (for `1b67a58`).** I10's `**Rule:**` adds the runtime delivery check
  (`macos_session_env_delivery_cmd`, exit 197, read as the refusal only when a credential was sent)
  and moves git's `GIT_CONFIG_*` helper out of `~/.augur-env` into the session's remote command

## What the code now does for I10 (at `4a9b970`, with the changes at `1b67a58`, `f93113a`, `3e0ac6c`, `d3b8b13`, `d6e4246` and `3161838`)

**At `3161838` (the eighth review's fixes).** Where the passages below (the `d6e4246` paragraph
included) differ, this paragraph wins.
- **The exits that are not refusals of the VM push too.** At `d6e4246` a running VM could still be
  left with an older augur's credential-bearing `~/.augur-env` by a check that exits before any push:
  the stale-egress-helper refusal (`require_fresh_egress_helpers`, the first check of `up`, `claude`
  and `shell --macos`, and the likeliest one right after an augur upgrade), and on `up`'s
  already-running branch the allowlist approval gate (declined, or unapproved and non-interactive),
  `start_proxy`'s exits, the base-VM check, and any command failing under `set -e` or a Ctrl-C.
  Now `require_fresh_egress_helpers` refuses a running macOS VM through `refuse_running_macos_vm`
  (its push reaches the guest through the gvproxy the refusal does not trust; it sends no
  credential), and the running branch sets an EXIT trap after the egress-mode check that runs
  `push_macos_guest_env <vm> --refusing`, disarmed just before the self-test (which stops the VM when
  it fails; the refusals after it push themselves). The base-VM check moved below the running
  branch: reconciling a running VM does not use the base. Each such run pushes exactly once.
  An early credential-free push on every running-VM entry was considered and not done: it would
  double every session's push and move `up`'s push ahead of its self-test, which test 56 pins the
  other way. Not covered: `require_vz` (with no VM backend augur cannot tell the VM runs) and a
  session's clock and timezone fixes between its refusals and its push, which are best-effort and do
  not exit.
- **The delivery check runs after the guest's startup files.** Recorded as an `Accepted trade-off`
  at `macos_session_env_delivery_cmd` and in ADR-0023; see Residual risks.
- **Executable bits.** Five test tiers (35, 39, 43, 51, 52) the branch had turned 100644 are 100755
  again; `git diff --summary c9068b2..HEAD | grep mode` lists only this file and ADR-0023.

**At `d6e4246` (the seventh review's fixes).** Where the passages below (the `d3b8b13` paragraph
included) differ, this paragraph wins.
- **The temp-file cleanup no longer depends on `mktemp`.** At `d3b8b13` the whole cleanup sat behind
  the guest's `mktemp` of its reference file, so a failing `mktemp` skipped even the plain
  `-mmin +1` removal of old `~/.augur-env.tmp.*` files (which may hold an older augur's
  credentials). The age test now always runs; the `-newer` clause is added only when the reference
  file was created (an `if [ -n "$_ref" ]` in the guest command, zsh- and POSIX-sh-safe, no
  word-split expansion).
- **No SSH transport is named, not retried.** `_macos_ssh_cmd` exits 1 when the VM's host or port
  cannot be resolved (a running egress VM whose gvproxy is down); inside the push's pipeline that
  exit read as the guest's "failed write" status 1, so the push said `~/.augur-env` could not be
  written and was retried. `push_macos_guest_env` now checks `macos_ssh_transport_ok` before the
  pipeline: without a transport it says so (and, with `--refusing`, that the old file may still hold
  credentials), sends nothing and returns 1, which `push_macos_guest_env_retrying` does not retry.
  `verify_macos_egress_locked`'s pre-check uses the same helper (same conditions as its inline test
  at `d3b8b13`), and its comment points at `_macos_ssh_cmd` instead of quoting lines that moved there.
- **The self-test record is renamed into place.** `macos_record_egress_verified` writes
  `<record>.tmp.<pid>` beside the record and `mv -f`s it over, so a concurrent
  `require_macos_egress_verified` reads the old record or the new one, never an empty file; a
  failed write removes both and returns 1, which the callers treat as an unrecordable pass.
- **Every refusal of a running VM now pushes first.** `require_macos_egress_mode_current` (a mode
  mismatch, or no mode record at all, which marks a VM started by an older augur, the one likeliest
  to hold a credential-bearing `~/.augur-env`) and `require_macos_admin_password --running` (only on
  `up`'s already-running branch) refuse through `refuse_running_macos_vm`. The push uses only augur's
  SSH key and sends no credential, so it is acceptable on a VM whose mode is wrong or unknown or that
  has no stored admin password. The `Deliberately not used by` note is gone; a stopped VM with no
  admin password is still refused before anything touches it.

**At `d3b8b13` (the sixth review's fixes).** Where the passages below (the `3e0ac6c`, `f93113a` and
`1b67a58` paragraphs included) differ, this paragraph wins. Its theme: failures made fatal for
safety stay fatal where they are security-relevant (refusals, a missing self-test record, a missing
drop-in), and transport hiccups and availability failures no longer stop a VM or a session at once.
- **An unrecordable pass no longer stops a running VM.** `macos_record_egress_verified` no longer stops
  anything: without a run id it removes any record (one written earlier in the same boot included),
  prints the error and returns 1. The boot path then stops the VM it just booted
  (`stop_unverified_macos_vm`, clone kept), as before. The already-running branch of `cmd_up_macos`,
  which at `f93113a` called the same stop, now refuses through `refuse_running_macos_vm` (the
  credential-free push, the message, exit 1) and leaves the VM running: it has just passed its
  self-test and may be serving live sessions, and a `ps` or `run.pid` read that failed once must not
  end them. Every session then refuses the VM until an `up` records a pass, so the change fails closed
  for new sessions and only stops tearing down existing ones.
- **A push that must succeed is tried once more, unless refused.** `push_macos_guest_env` now returns
  1 (cannot work: nothing sent, or `~/.zshenv` not updated), 2 (`MACOS_PUSH_REFUSED_RC`: the
  acceptance check refused, whatever later step failed) or 3 (`MACOS_PUSH_RETRYABLE_RC`: a failed write
  with the old file in place, or ssh's 255 / any unknown outcome). `push_macos_guest_env_retrying`
  runs it once more, at once, on 3 only, and is what the boot (`require_macos_session_env_accepted`),
  `up` on a running VM and every session (`prepare_macos_session`) call; only a second failure stops
  the boot's VM or exits. A refusal is never retried; neither is an unwritable `~/.zshenv` (it fails
  the same way every time) nor a push that sent nothing. The refusal pushes (`--refusing`) are not
  retried either; the refusal stands regardless. The guest-side exit codes (`_acc`, +10) are
  unchanged.
- **The temp-file cleanup spares a concurrent push's file.** The cleanup's reference file is now
  touched (`touch -t`) to a minute after the guest's current time (formatted by `date -r <seconds>`,
  BSD, or `date -d @<seconds>`, GNU), so `-newer` matches only files dated more than a minute ahead.
  At `3e0ac6c` the reference had the mtime of its own creation, so a concurrent push's temp file
  created after it was removed and that push
  failed. If neither `date` form works, the reference keeps its creation mtime (the `3e0ac6c`
  behaviour); a guest-clock step between two concurrent pushes can still make one's file look stale.
  Either way the losing push fails with status 3 and is retried once. A stale file dated less than a
  minute ahead survives until a later push finds it older than a minute.
- **One refusal helper.** `refuse_running_macos_vm <vm> <lines…>` pushes `~/.augur-env` with
  `--refusing`, prints the lines and exits 1. `require_macos_egress_verified`,
  `resolve_running_macos_vm_credentials` and the unrecordable-pass refusal above call it, and its
  header is now the one place the rule ("every refusal of a running VM rewrites `~/.augur-env` first")
  is explained. `require_macos_egress_mode_current` and `require_macos_admin_password` deliberately do
  not use it (a `Deliberately` note there): they run before augur's first connection to the guest, and
  their remedies restart or recreate the VM, whose boot pushes before any session.
- **The names are computed once.** `macos_session_accept_env_line` and `macos_session_env_check_cmd`
  take the names as an argument and validate nothing; `macos_session_env_names` stays the one place
  they are checked, and the install, the pre-save re-check and the push each call it once.
- **No raw grep error on an old base.** The acceptance check is `grep -sqxF`, so a guest with no
  drop-in is refused without `grep: …: No such file or directory` on the operator's terminal; the
  pre-save re-check runs the same command.
- **Which host processes hold the values.** The `ssh_macos_session` comment said the session ssh "is
  the only process that holds" a file- or `gh`-sourced value. augur's own bash holds it as a shell
  variable (`_creds`), and every subshell it forks while `_creds` is set holds that memory too. The
  comment, ADR-0023 and I10 now say that the value is in the environment of the session ssh only (no
  other child's environment, never argv, never disk), and that augur's own process memory and its
  forked subshells hold it as shell variables. Nothing in the code changed for this.

**At `3e0ac6c` (the fifth review's fixes).** Where the passages below (the `f93113a` and `1b67a58`
paragraphs included) differ, this paragraph wins:
- **The run id is read in UTC.** `macos_vm_run_id` runs `LC_ALL=C TZ=UTC0 ps -o lstart= -p <pid>`.
  `lstart` is local time, so at `f93113a` an augur run whose `TZ` differed from the run that wrote the
  record (another terminal, a shell that sets `TZ`) computed another id for the same process and
  refused the VM. A record written at `f93113a` (local time) does not match the UTC id; the VM is
  refused once, and `augur up --macos` re-records it.
- **The missing-self-test refusal pushes first.** `require_macos_egress_verified`, when it refuses,
  first runs `push_macos_guest_env "$vm" --refusing || true`, so an older augur's credential-bearing
  `~/.augur-env` no longer survives that refusal. The push sends no credential (it never reads
  `_creds`), which is why it is done on a VM whose containment is unproven (a `Deliberately` comment).
  `--refusing` makes a push that could not rewrite the file (exit 1) or whose outcome is unknown
  (ssh's 255) also warn that the file may still hold an older augur's credentials, as the old-base
  refusal already did; the refusal follows either way. `resolve_running_macos_vm_credentials` passes
  `--refusing` too. The fact "an older augur's `~/.augur-env` holds credentials, so every refusal of a
  running VM pushes first" is explained once, in `push_macos_guest_env`'s header; the other sites point
  there.
- **Every push checks acceptance.** `push_macos_guest_env`'s `--require-session-env` parameter and its
  plain branch are gone (every caller passed it); the acceptance check is always step 0.
- **The pre-save re-check runs the clones' check too.** `verify_macos_session_env_acceptance` appends
  `macos_session_env_check_cmd` (the exact `AcceptEnv` line in the drop-in, the command every clone's
  `up` and session run) to its root script after the `sshd -T` test, exiting 5 with a message naming
  the drop-in and the line. A base whose sshd accepts the names from another file, or whose drop-in
  names them in another order, is no longer saved.
- **One joiner for the names.** `macos_session_accept_env_line` is built from `macos_session_env_names`
  (each name through `valid_env_name`) and fails with it; `macos_session_env_check_cmd` and the install
  propagate that failure, so a push with an invalid name sends nothing.
- **The exit-197 message.** `macos_session_env_refused delivery` now says the session exited with 197,
  the status the delivery check uses when the guest's sshd did not pass on a credential (the agent or
  shell then never started), to ignore it if the agent or shell itself exited with 197, and to run
  `augur up --macos` first (it re-checks the drop-in); only if that passes and sessions keep exiting
  with 197 does it name the recreate (`augur destroy --macos && augur up --macos`, after
  `augur update --macos` if the base is out of date). The mechanism is unchanged.
- **git's exports stay where they are.** `git_credential_env`'s accepted trade-off (a guest startup
  file that exports `GIT_CONFIG_*` replaces augur's set) now says why the exports were not moved inside
  the agent's `zsh -l -c`: every zsh the agent starts for a command reads `/etc/zshenv` and `~/.zshenv`
  again, so git there would still see the startup file's set, and the interactive shell has no point
  after its startup files short of replacing them.
- **One helper for guest output.** `show_guest_lines` (sanitize, then one `  | <line>` error line per
  non-empty line) replaces the six inline copies of the `sanitize_guest_lines | while read` loop and
  `macos_session_env_show_err`. Blank lines are now skipped at the log-tail sites too.

**At `f93113a` (the fourth review's fixes).** Where the passages below (the `1b67a58` paragraph
included) differ, this paragraph wins:
- **The boot id is the pid plus its start time.** `macos_vm_run_id` reads the pid from `run.pid`
  (whitespace stripped, digits only) and prints `<pid> <start time>`, the start time from
  `LC_ALL=C ps -o lstart= -p <pid>` with its padding collapsed. It prints nothing when the pidfile is
  missing, holds no pid, or no process has that pid, and nothing matches an empty id. So a record
  written for an earlier boot does not match a hand-started `augur-vm run` that got the same pid
  after a host crash.
- **No run id after a passed self-test fails `up`.** `macos_record_egress_verified` used to warn and
  return 0 (sessions then refused the VM). It now prints why, calls `stop_unverified_macos_vm` (VM,
  gvproxy and proxy stopped, record removed, clone kept) and exits 1, on the boot path and on the
  already-running branch.
- **The refusal names `augur up --macos`.** `require_macos_egress_verified` ends with "Run `augur up
  --macos` to re-run the egress self-test on the running VM" instead of "Restart it: `augur down

  old-base VM it then refuses with the old-base remedy, and the first message promises only the
  self-test.
- **One push on a boot.** The `push_macos_guest_env` at the end of `cmd_up_macos`'s boot path is gone
  (a comment marks it `Deliberately`). The boot's only push is `require_macos_session_env_accepted`'s,

  `DEVELOPER_DIR`, `agent_fixed_env`), and nothing between the two places wrote `~/.augur-env` or
  `~/.zshenv` (the clock and screen-lock steps, the self-test, the timezone, `ensure_*`, the
  `.claude.json` seed, the `~/.gitconfig`
  scp), so the second push rewrote identical bytes. The running path (`up` on a running VM,
  `prepare_macos_session`) still pushes once.
- **The drop-in's root script is not staged.** `install_macos_session_env_acceptance` no longer writes
  `~/.augur-session-env-install.sh` and runs it with `sudo -S sh` over a second connection (a window in
  which any guest-user process could swap it and run as root in the future base). `macos_run_root_script`
  pipes `{ macos_admin_password_stdin "$vm" && printf '%s\n' "$MACOS_ROOT_SCRIPT_BEGIN" "$script"; }`
  into one `ssh_macos "$vm" "sudo -S -k -p '' /bin/sh -c '<skip to the marker>; exec /bin/sh -s'"`.

  ignores a cached credential that would skip that read; under NOPASSWD (the build's grant is still in
  place when the build installs the drop-in) sudo reads nothing, and the root shell's `read` loop
  discards lines up to the marker (`#augur-root-script`, a shell comment), so the password line never
  reaches the script shell either way. A wrong password makes sudo take the next lines as retries and
  fail: no line of the script runs. Exit codes 2/3 (from the script) and 4 (no fresh connection) are
  unchanged; the script's `sshd -T` runs with `</dev/null` since the script itself is on stdin. The
  check code (`accepts`) is one generator, `macos_session_env_accepts_sh`.

  custom provisioning; the build's before the Xcode selection, the sudo revoke and the signature check).
- **Names from the list.** `macos_session_env_names` reads `session_credential_names` and checks each

**How the values reach the ssh process.** `ssh_macos_session` first builds the remote command
(`macos_session_env_delivery_cmd` in front of the caller's last argument, below), then resolves the ssh

each entry (a builtin, no argv) and `exec`s the ssh. Argv carries only `SendEnv=<NAME>` options and the
remote command string, which holds names and no value. A file- or `gh`-sourced value lives in that one

exported into augur's own environment is inherited by augur and every child anyway (none forwards it).

## Residual risks

- **Host-side process-env visibility.** For the session's life, the values sit in the host `ssh`
  process's environment. INVARIANTS, ADR-0023 and the `ssh_macos_session` comment now all say macOS is
  **expected** to serve another process's environment only to its own user and root, who can already
  read the host files and `gh` token, and that this is **not yet observed on a Mac** (`ps -E` from a
  second account). Plain `ps` does not print environments.
- **Host-env-sourced credentials are already in augur's environment.** When `ANTHROPIC_API_KEY` /
  `CLAUDE_CODE_OAUTH_TOKEN` come from the operator's environment rather than their host file, augur's
  own process and **every** child (each `ssh_macos`, `augur-vm`, `gh`, …) inherit them anyway. They are
  not forwarded: `ssh_macos` is hermetic and sends no `SendEnv`. ADR-0023 and the `ssh_macos_session`
  comment now claim "only this ssh holds it" for file- and `gh`-sourced values only, and the comment
  (`:1024`) records the rest as an `Accepted trade-off`. Test 56 asserts the narrower form. At
  `d3b8b13` the comment, ADR-0023 and I10 also say that augur's own bash and the subshells it forks
  hold file- and `gh`-sourced values as shell variables in memory; "only this ssh" is about
  environments (and argv and disk), not process memory.
- **Old credential bytes in free disk blocks.** Rewriting a credential-bearing `~/.augur-env` an older
  augur wrote (or removing an old `~/.augur-env.tmp.*`) frees the blocks without overwriting them, so a
  persisted clone may still hold the old tokens in free space. ADR-0023 records this, and so does the
  `push_macos_guest_env` comment (`:4234`, `Accepted trade-off`). The remedy for old bases,
  `destroy --macos && up --macos`, deletes the clone.
- **Relies on the helper-chain reset in `git_credential_env` (on `main` since #277).** After a
  successful push, git's `store` step hands the credential to every configured helper, including the
  system or host `osxkeychain` helper, which can write it into the guest's login keychain **on disk** if
  that keychain is unlocked. "Nothing on the guest disk" holds for `GH_TOKEN` because the first
  `GIT_CONFIG_*` entry (in `~/.augur-env` at `4a9b970`; at `1b67a58` the first export of the session's
  remote command) is an empty `credential.https://github.com.helper`, which clears every helper
  collected from the config files before augur's. ADR-0023 records this ("Depends on").
  Test 35 pins it against real git with `GH_TOKEN` set as the session ssh sets it, and that a guest
  shell augur did not open gets none of the `GIT_CONFIG_*` set and git asks its own helpers there (at
  `4a9b970` through the guard; at `1b67a58` because no file holds the set, even for a shell with a
  `GH_TOKEN` of its own). Residual: at `1b67a58` the exports run in sshd's shell, before the login zsh
  the remote command starts reads its startup files, so a `GIT_CONFIG_*` set any guest startup file
  exports (`/etc/zshenv`, `~/.zshenv`, `~/.zprofile`, `~/.zshrc`) replaces augur's, reset included
  (`Accepted trade-off` at `git_credential_env`; test 35 pins it), and `git -c credential.helper=…` on
  a command line is read after it. Both are in the guest's own hands. Outside augur's sessions the
  guest's own helpers (Apple git's `osxkeychain` included) run as without augur; no augur credential
  is there to hand them.
- **Pre-self-test guest interaction on the boot path.** Every boot now runs one
  `push_macos_guest_env --require-session-env` before the self-test (at `4a9b970` with `_creds` emptied;
  at `1b67a58` the push reads no `_creds`): the check, the
  non-secret `~/.augur-env` (no `GIT_CONFIG_*` lines) and the `~/.zshenv` line. The clock fix and
  `configure_macos_guest_session` follow, both before the self-test as on `c9068b2`. None of them sends an
  agent or gh credential (the clock and screen-lock steps feed `sudo -S` the guest's own admin password,
  as before), so I1's "no credential to an unproven guest" holds. The comment above them (`:4718-4732`)
  names exactly these three steps. Since `4a9b970` a failure of the first one stops the VM, so no
  un-self-tested VM is left for a later session to attach to; the clock and screen-lock steps are
  best-effort and never exit. At `d3b8b13` a first push that failed with a dropped connection or a
  failed write is tried once more before the VM is stopped, so up to two such pushes precede the
  self-test; both are built from the same host-side constants and carry no credential, and a refusal
  still stops the VM after the first.
- **An interrupted boot (closed at `1b67a58`).** At `4a9b970`, an `up --macos` killed between
  `augur-vm run` and the self-test (Ctrl-C, a kill, a host crash) left a running VM that the next
  `claude`/`shell --macos` attached to and sent credentials, with no self-test. At `1b67a58` the session
  refuses unless the passed-self-test record matches the VM's current run id. It rests on
  `augur-vm run` keeping one pid in `run.pid` for the boot (it writes `getpid()` once and removes the
  file on exit, `RunSession.swift`), which is not observed on a Mac. A guest cannot forge the record:
  it is a host file. At `f93113a` the id is the pid plus that process's `ps -o lstart` start time, so a
  hand-started `augur-vm run` that gets the old record's pid after a host crash no longer matches it;
  it now also rests on `ps -o lstart` printing one value for the process for the whole boot (across
  host sleep and clock syncs), likewise unobserved on a Mac. If either changes mid-boot, sessions
  refuse until `up --macos` records the pass again; neither can make a session attach. One
  full-suite run of test 56 failed from mid-file on with every record mismatched, before test 56 had
  its `lstart` stand-in. At `3e0ac6c` this was looked at again: on this host procps-ng 4.0.4's
  `lstart` equals `/proc/stat`'s `btime` plus the process's start ticks (checked for pid 1 and the
  test shell), and `btime` did not move over 85,000 reads in 60 s, so it is not a per-call
  recomputation; it moves only when the kernel's real-time clock is stepped (this host is a VM, whose
  clock is resynced), which shifts every process's start time at once, the failure's shape. `TZ`
  played no part there (no test sets it, and both reads ran in one environment), but it would have
  in production, hence the UTC read. Tests 51 and 56 answer `lstart` from a stand-in, and test 51's
  real-`ps` section retries a check only when the test shell's own start time moved while it ran;
  51 and 56 passed ten runs each in a row. macOS's `ps` is expected to print the start time the
  kernel recorded for the process, which a clock step may also shift; unobserved. An `up` that
  cannot read the id after a passed self-test fails; at `d3b8b13` it removes any record and stops the
  VM only on a boot, leaving a running VM running (refused by every session until a pass is recorded).
- **The drop-in's root script could be swapped (closed at `f93113a`).** Up to `1b67a58` it was written to
  `~/.augur-session-env-install.sh` over one connection and run by `sudo -S sh` over a second, so any
  process of the guest user could replace it in between and run as root in the VM that becomes every
  project's base. At `f93113a` the password line, a marker and the script travel on one connection's
  stdin and nothing is staged. Residual: the protocol relies on the guest's `sudo -S` reading only the
  password line and on its `/bin/sh` `read` loop and `sh -s` taking the rest; test 56 runs it with a
  `sudo` stand-in under bash and dash, not on macOS.
- **The delivery check's exit status is not unique.** An agent or shell that itself exits 197 after a
  credential was sent is reported as the delivery refusal (`Accepted trade-off` in
  `ssh_macos_session`; at `1b67a58` a session that sent nothing passes 197 through). That costs a
  misleading message after the session ended, never a credential. At `3e0ac6c` the message says the
  session exited with 197, what the delivery check means by it, to ignore it if the agent or shell
  itself exited so, and to run `augur up --macos` before recreating the VM.
- **The delivery check runs after the guest's startup files.** sshd runs the remote command through
  the login shell's `-c`, and zsh reads `~/.zshenv` (and what it sources) before any command, so a
  guest startup file that exports one of the credential names hides a value the sshd dropped: the
  session starts with that file's value, not augur's (`Accepted trade-off` at
  `macos_session_env_delivery_cmd`, ADR-0023). augur's own `~/.augur-env` never sets those names
  (test 56). No earlier point in an ssh session runs a command, and the files are the guest's own,
  writable by the agent; it costs a session running with the guest's credential instead of failing,
  never an exposure of augur's.
- **A push can remove a concurrent push's temp file.** At `4a9b970` any checked push did; at `1b67a58`
  only one created in the instant between another push's `mktemp` reference file and its `find`. The
  concurrent push's `mv` then fails and it reports a failed write (`Accepted trade-off`, in
  `push_macos_guest_env`); augur does not support two commands on the same project at once anyway.
  At `d3b8b13` the reference is touched to a minute ahead, so a concurrent push's file is no longer
  removed for being newer than the reference; only a guest-clock step between the two pushes (or a
  guest where neither `date -r` nor `date -d @` works) can still make it look stale, and the push that
  loses its file is tried once more (status 3, `push_macos_guest_env_retrying`).
- **A post-install probe failure leaves the drop-in live.** If the fresh connection after the drop-in
  install fails, nothing rolls it back. Only a scratch VM kept with `AUGUR_KEEP_BUILD_VM=1` survives that
  failure; no base VM is saved. Recorded as an `Accepted trade-off` (`:4115`) and in ADR-0023.
- **An old base still needs a successful update.** `update --macos` now installs the drop-in before any
  network step, but the update still saves the base VM only after every step (Homebrew, provisioning, the
  signature check) passed. While a Homebrew upgrade or a download keeps failing, an old base stays without
  the drop-in and its clones keep being refused; a full `build --macos` needs the network too.
- **A guest that lies to the acceptance check** gains nothing (ADR-0023, comment above
  `macos_session_env_check_cmd`): its own sshd decides what it accepts, and a session whose credentials
  it drops is refused by the delivery check.
- **A guest startup file can replace git's helper set.** A `GIT_CONFIG_*` set exported from
  `/etc/zshenv`, `~/.zshenv`, `~/.zprofile` or `~/.zshrc` replaces augur's, reset included
  (`Accepted trade-off` at `git_credential_env`). At `3e0ac6c` moving the exports into the agent's
  `zsh -l -c` was considered and not done: every zsh the agent starts for a command reads the zshenv
  files again, so git there would still see the startup file's set. Only the guest user's own files
  or root can set one, and it costs at worst the reset (a helper such as `osxkeychain` getting
  `store`), not an argv exposure.
- Carried unchanged: the reuse-path self-test spoofing caveat (item 46's project-VM half in 2026-11-05),
  and the macOS admin password exclusion in I10's Note.

## macOS 27 guest facts the design relies on

**Observed** (ADR-0023, on a clone of the base VM, 2026-11-07; not re-observed here, since this host has
no Mac):
- `/etc/ssh/sshd_config` has `Include /etc/ssh/sshd_config.d/*` (absolute, near the top), and
  `sshd_config.d` holds only macOS's own `100-macos.conf` (root:wheel, 644).
- `sudo sshd -T` prints `AcceptEnv LANG` and `AcceptEnv LC_*`: mixed-case keyword, one name per line.
  `5ba0a2a` makes test 56's sshd shim print this form by default (`SSHD_LOWER=1` selects upstream's
  lowercase), and the install's `awk 'tolower($1) == "acceptenv"'` accepts both.
- `launchctl print system/com.openssh.sshd` shows a LaunchDaemon with `active count = 0` while a session
  is open, consistent with one sshd per connection. That is why the candidate is verified before it goes
  live.

**Still Mac-only and unobserved:**
- that macOS serves another user's process environment only to that user and root;
- that `sshd -T -f <test config>` follows the staged config's absolute `Include` as described;
- end-to-end delivery: the `SendEnv` values present in a `claude`/`shell --macos` session (the
  guest-side delivery check now refuses a session where they are not), and absent from a plain `ssh`;
- that a GUI Terminal or plain `ssh` shell in the guest gets no `GIT_CONFIG_*` and its HTTPS git still
  works through the guest's own helpers, and that a `claude`/`shell --macos` session's agent and shell
  have the set the remote command exports (at `1b67a58`);
- that a VM refused at boot is really stopped by `augur-vm stop` (test 56 sees only the call);
- that `augur-vm run`'s `run.pid` holds one pid for the whole boot, so the passed-self-test record keeps
  matching while the VM runs (at `1b67a58`), and that `ps -o lstart=` prints the same start time for
  that process for the whole boot, across host sleep and clock syncs (at `f93113a`), and that BSD `ps`
  honours `TZ=UTC0` for it (at `3e0ac6c`);
- that the guest's `sudo -S -k` takes only the password line of `macos_run_root_script`'s stdin, with
  and without the build's NOPASSWD grant, and that the guest's `/bin/sh` skips to the marker and runs
  the rest with `sh -s` (at `f93113a`);
- a real guest's process list during a session;
- the BSD-userland behaviour of the push (`find -mmin`, `find ! -name`, and at `1b67a58`
  `find \( -mmin +1 -o -newer "$_now" \)` with `mktemp /tmp/augur-env-now.XXXXXX`; `umask`, `mv`) and of
  the root script (`mktemp`, `grep -qxF`, `awk`), which test 56 exercised with GNU tools; and zsh running
  the delivery check and the session's `export` prefix, which tests 35 and 56 ran under bash and `sh`.

## Contract vs code

No divergence on I10's argv property: the only credential-bearing ssh puts names, never values, on argv,
and test 56 enforces it through a real `ssh` shim. The three wording divergences recorded at `5ba0a2a`
are fixed at `baccfcd`:
- INVARIANTS no longer states the host-side environment visibility as fact (it matches ADR-0023's "not
  yet observed");
- ADR-0023 and the `ssh_macos_session` comment narrow "no other process holds the values" to file- and
  `gh`-sourced credentials, with an `Accepted trade-off` for env-var-sourced ones;
- INVARIANTS mentions the scrub of a refused guest's `~/.augur-env`.

One more wording divergence, found by the sixth review, is fixed at `d3b8b13`: the `ssh_macos_session`
comment and ADR-0023 said the session ssh is the only process that holds a file- or `gh`-sourced value,
while augur's own bash holds it as a shell variable and its forked subshells inherit that memory. Both,
and I10, now say the value is in the session ssh's environment only (no other child's environment,
never argv, never disk) and in augur's own and its forked subshells' memory as a shell variable. The
argv property was never affected.

INVARIANTS' "never written to the guest's disk" for `GH_TOKEN` relies on the helper-chain reset in
`git_credential_env`, which `main` has since #277; at `baccfcd` that was an open dependency. I10 now
names the reset and lists test 35 for it; see Residual risks.

## I10's mark
