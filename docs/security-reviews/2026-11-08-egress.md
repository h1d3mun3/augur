## What changed in the contract

`git log 70c5061..HEAD -- docs/security-reviews/INVARIANTS.md` lists `ca2ebf8` and `38f5a89`; the net
diff is confined to I10 and the closing summary.

- **`**Rule:**` (`INVARIANTS.md:161-178`).** Before: on macOS the credentials are written to
  `~/.augur-env` via SSH stdin by `push_macos_guest_env` on every `up` / `claude` / `shell --macos`. Now:
  in macOS VM mode they reach the guest **only as the environment of the interactive ssh** that starts
  `augur claude --macos` / `augur shell --macos` (`ssh_macos_session`). A subshell `export`s the values
  and execs that one `ssh`, which names exactly the resolved variables with `-o SendEnv=<NAME>` (never
  `-o SetEnv=NAME=value`). The guest's sshd accepts exactly those names through a root-owned drop-in that
  the base VM build/update writes (`install_macos_session_env_acceptance`). A guest without it is refused
  before any credential is sent (`macos_session_env_check_cmd`). Credentials are never written to the
  guest's disk: `~/.augur-env` holds only non-secret per-VM env, and augur's other ssh calls carry no
  `SendEnv`. New closing sentence: on the macOS host the values sit in that one `ssh` process's
  environment for the session's life, readable only by the same user and root. The Container sentence
  and the `setup-token --macos` sentence are unchanged.
- **`**Why:**` (`:179-182`).** Adds the macOS reason: keeping credentials out of `~/.augur-env` keeps
  them off the clone's disk, which `down --macos` persists.
- **`Enforced by` (`:183-196`).** macOS mode now reads: `tests/56_macos_session_credentials.sh`, through
  a recording `ssh_macos` **and an `ssh` shim on PATH**, asserts that the session ssh carries
  `-o SendEnv=` for exactly the resolved names with the values only in its own environment; that no
  value is on any ssh/scp argv, in any guest file (`~/.augur-env` included) or (for file- and
  `gh`-sourced values) in any other ssh call's environment; that build/update write the `AcceptEnv`
  drop-in; and that a guest without it gets no session. Review-only (Mac-only): that a real guest sshd
  honours the drop-in, and the guest's process list. The Container and `tests/52` sentences are
  unchanged.
- **Summary (`:209-217`).** I10's partial coverage now reads "the macOS session ssh's argv and
  environment" instead of "the macOS `~/.augur-env` push's ssh argv". The review-only remainder is now
  "a real guest sshd honouring the `AcceptEnv` drop-in, and a real guest's process list".
- **Marks.** `diff <(git show 70c5061:docs/security-reviews/INVARIANTS.md | grep '^#') <(grep '^#'
  docs/security-reviews/INVARIANTS.md)` is empty: every heading line, marks included, is identical. I1–I8
  ✅, I9 🟡, I10 🟡.

## What the code now does for I10 (at `5ba0a2a`)

**Resolution is unchanged.** `resolve_session_credentials` (`augur:525`), `validate_secret_value`
(`:472`), `resolve_api_key` and `session_credential_env` (`:2913`) are code-identical to `70c5061` with
comments stripped. `session_credential_names` (`:552`) is new: each `agent_auth_specs` guest variable,
then `GH_TOKEN`.

**Which ssh carries `SendEnv`.**
- **Only `ssh_macos_session`** (`augur:983-990`), which has exactly two callers: `cmd_claude_macos`'s
  launch (`:4794`) and `cmd_shell_macos`'s (`:4804`). `SendEnv=` appears in one line of non-comment code
  in `augur` (`:986`), which test 56 pins.
- **None on every other ssh.** `ssh_macos` (`:919-923`) is unchanged in behaviour; it is now a thin
  wrapper over `_macos_ssh_cmd` (`:928-957`), which builds the same option array: `-F /dev/null`, `-p
  <gvproxy forward port>`, `StrictHostKeyChecking=accept-new`, the per-VM known-hosts file,
  `LogLevel=ERROR`, `ConnectTimeout=10`, `ServerAliveInterval=15`, `ServerAliveCountMax=4`, the key
  options, then `user@host`. A diff of the old `ssh_macos` against the new `ssh_macos` +
  `_macos_ssh_cmd` (comments stripped) shows only the move into arrays; the option list, its order, and
  the `exit 1` on an unresolvable host/port are the same. `macos_ssh_host` / `macos_ssh_port` (the
  gvproxy forward) are code-identical. No `ControlMaster`/`ControlPath` (comment at `:948`), so the env a
  session sends belongs to its own connection. `scp_to_macos` (`:993`), `ssh_macos_provision` and
  `ssh_macos_provision_stdin` are code-identical.
- **`setup-token --macos`.** `cmd_setup_token_macos` (`:4975`) is code-identical. Its login ssh is a plain
  `ssh_macos … -t` (`:5037`), so it has no `SendEnv`, and it does not call the resolver.

**How the values reach the ssh process.** `ssh_macos_session` first resolves the ssh command in augur's
shell (`_macos_ssh_cmd`, so the host/port lookups never see a value), builds `-o SendEnv=${_kv%%=*}` for
each `_creds` entry (names only), then in a subshell runs `export "$_kv"` for each entry (a builtin, no
argv) and `exec`s the ssh (`:984-989`). Argv carries only `SendEnv=<NAME>` options and the remote command
string, which holds no value. The values live in that one ssh process's environment.

**What `~/.augur-env` still holds.** `push_macos_guest_env` (`:4196-4253`) writes a header, the
Homebrew `shellenv` eval, the agent's PATH, `DEVELOPER_DIR` and `agent_fixed_env` (`:4200-4209`;
`DISABLE_AUTOUPDATER=1` for Claude), then the end marker. No `_creds` entry is written (test 56 asserts
the old credential loop is gone). It still wires git's credential helper when `creds_have_gh_token`
(`:561`), and the helper holds only the `$GH_TOKEN` reference (`macos_git_credential_helper_cmd`,
`:4157`). The atomic write (umask 077 temp file, end-marker check, rename), the age-based temp cleanup and
the exit-code outcomes (0 / 1 / 3 / 4 / other) are as recorded on 2026-11-07, plus exit 5 (below). The
file is rewritten whole, so the first push to a guest whose file an older augur wrote removes the
credentials from it. A failed push is now **fatal for a session** too (`prepare_macos_session`, `:4731`):
`~/.zshenv` sources the file after sshd has set the session env, so a stale `export GH_TOKEN=…` would
replace the fresh value.

**The drop-in: install / verify / rollback.** `install_macos_session_env_acceptance` (`:4036-4079`),
called fatally by `cmd_build_macos` (`:3741`) and `cmd_update_macos` (`:5711`, on the staging clone; the
base VM is left as-is on failure), before the final integrity check and save.
- Writes `/etc/ssh/sshd_config.d/200-augur-session-env.conf` (`:4016`) holding one line,
  `AcceptEnv ANTHROPIC_API_KEY CLAUDE_CODE_OAUTH_TOKEN GH_TOKEN` (`:4017-4020`). The names are exact (no
  patterns) and are checked against `^[A-Za-z_][A-Za-z0-9_]*$` before they reach the root script
  (`:4042-4044`).
- The script is staged in the guest user's home over ssh stdin, then run by `sudo -S` with the admin
  password on stdin (`:4068-4069`), so the password is on no argv.
- As root: the candidate is written to `/etc/ssh/augur-session-env.candidate` (root:wheel, 644), and a
  test config (an `Include` of the candidate, then a copy of `/etc/ssh/sshd_config`) is checked with
  **one** `sshd -T -f <test config>` run. `accepts` lowercases the keyword and reads every field, so both
  macOS's `AcceptEnv NAME` and upstream's `acceptenv` forms pass (`:4054-4060`). Exit 2 if it fails (the
  candidate never goes live) (`:4062`).
- Only then `mv -f` into `sshd_config.d` (`:4063`). The live config is checked the same way, and the
  drop-in is removed if that fails (exit 3, `:4064`).
- One fresh `ssh_macos … true` must then succeed (exit 4 otherwise, `:4073-4075`). On any failure,
  sshd's stderr is shown through `sanitize_guest_lines` and the function returns 1.

**Old bases: refusal and scrub.** `macos_session_env_check_cmd` (`:4750-4752`) is `grep -qxF '<the exact
AcceptEnv line>' <drop-in>`, so a base built for different names is refused too.
- **Boot path.** `cmd_up_macos` calls `require_macos_session_env_accepted` (`:4769-4780`) right after the
  SSH wait (`:4625`), before the clock, the self-test and the wiring. On exit 1/2 (line absent or file
  missing) it first runs the non-checking push (`push_macos_guest_env "$vm" || true`, `:4775`), which
  rewrites `~/.augur-env` without credentials. It then prints the remedy (`macos_session_env_refused`,
  `:4755`: `augur update --macos`, then `augur destroy --macos && augur up --macos`) and exits 1. Any other
  status (ssh failure) refuses without the push. The VM is left running.
- **Running VM.** Both `cmd_up_macos`'s already-running branch (`:4532`, after the self-test at `:4524`
  and the resolve at `:4531`) and `prepare_macos_session` (`:4731`) call
  `push_macos_guest_env … --require-session-env`. The check runs first in the same ssh session and only
  sets `_acc` (`:4231`). The env file and `~/.zshenv` line are still written, then `[ $_acc = 0 ] || exit 5`
  (`:4235`), before the git helper. The host maps 5 to `macos_session_env_refused` and returns 1, and
  both callers `exit 1`. So a refused guest is scrubbed of credentials an older augur wrote, gets no
  git helper, and gets no session ssh.
- No fallback to writing credentials to disk and no in-place patching of project VMs, per ADR-0023.

**What `up --macos` delivers.** No credential: it never calls `ssh_macos_session`. It still resolves and
validates (`:4544` before the clone; `:4531` on the running branch), and the result decides whether the
push wires the git helper. A `claude`/`shell --macos` that boots through `cmd_up_macos` reuses the
caller's `_creds` (`cmd_up_macos` no longer declares its own `local _creds`).

**Container mode — unchanged.** `cmd_claude` (`:3021`) and `cmd_shell` (`:3054`) are code-identical:
they resolve (`:3028`, `:3059`) and pass `--env-file <(session_credential_env)` to `eng exec` (`:3046`,
`:3069`). `container run` still gets no credential.

**Accepted trade-offs, as commented in code (carried, not new).**
- No fresh self-test before a `claude`/`shell --macos` session on a running VM (`:4725-4730`).
- The concurrent-command gaps in `prepare_macos_session` (`:4702-4705`).
- The duplicate `~/.zshenv` line from two racing pushes (`:4222-4224`).

The branch adds no new `Accepted trade-off` comment.

## Residual risks

- **Host-side process-env visibility.** For the session's life, the values sit in the host `ssh`
  process's environment. INVARIANTS, ADR-0023 and the `ssh_macos_session` comment say macOS serves
  another process's environment only to its own user and root, who can already read the host files and
  `gh` token. ADR-0023 lists this as **not yet observed on a Mac** (`ps -E` from a second account). Plain
  `ps` does not print environments.
- **Host-env-sourced credentials are already in augur's environment.** When `ANTHROPIC_API_KEY` /
  `CLAUDE_CODE_OAUTH_TOKEN` come from the operator's environment rather than their host file, augur's
  own process and **every** child (each `ssh_macos`, `augur-vm`, `gh`, …) inherit them anyway. They are
  not forwarded: `ssh_macos` is hermetic and sends no `SendEnv`. But "augur's own shell and every other
  child never hold them" (ADR-0023, `ssh_macos_session` comment `:966-968`) holds only for file- and
  `gh`-sourced values. Test 56 asserts exactly that narrower form, and INVARIANTS makes no such claim. No
  code comment records this as an Accepted trade-off.
- **Old credential bytes in free disk blocks.** Rewriting a credential-bearing `~/.augur-env` an older
  augur wrote (or removing an old `~/.augur-env.tmp.*`) frees the blocks without overwriting them, so a
  persisted clone may still hold the old tokens in free space. ADR-0023 records this ("augur does not
  scrub them"). The remedy it prescribes for old bases, `destroy --macos && up --macos`, deletes the clone.
  No code comment carries it.
- **Pre-self-test guest interaction on the boot path grows.** `require_macos_session_env_accepted` now
  runs before the boot self-test, and on a refused guest so does a `push_macos_guest_env`, which writes
  the non-secret `~/.augur-env`, the `~/.zshenv` line and (with a host gh token) the `$GH_TOKEN`-reference
  git helper. No credential value goes to the guest before the self-test, so I1's "no credential to an
  unproven guest" holds. The comment above `sync_macos_guest_clock` (`:4627-4630`) still calls the clock
  fix "the one step that precedes the self-test", which was already loose (`configure_macos_guest_session`
  also precedes it) and is now looser.
- **A guest that lies to the acceptance check** gains nothing (ADR-0023, comment at `:4746-4749`): its own
  sshd decides what it accepts, and the worst case is a session without credentials.
- Carried unchanged: the reuse-path self-test spoofing caveat (item 46's project-VM half in 2026-11-05),
  and the macOS admin password exclusion in I10's Note.

## macOS 27 guest facts the design relies on

**Observed** (ADR-0023, on a clone of the base VM, 2026-11-07; not re-observed here, since this host has
no Mac):
- `/etc/ssh/sshd_config` has `Include /etc/ssh/sshd_config.d/*` (absolute, near the top), and
  `sshd_config.d` holds only macOS's own `100-macos.conf` (root:wheel, 644).
- `sudo sshd -T` prints `AcceptEnv LANG` and `AcceptEnv LC_*`: mixed-case keyword, one name per line.
  `5ba0a2a` makes test 56's sshd shim print this form by default (`SSHD_LOWER=1` selects upstream's
  lowercase), and the install's `awk 'tolower($1) == "acceptenv"'` accepts both.
- `launchctl print system/com.openssh.sshd` shows a LaunchDaemon with `active count = 0` while a session
  is open, consistent with one sshd per connection. That is why the candidate is verified before it goes
  live.

**Still Mac-only and unobserved:**
- that macOS serves another user's process environment only to that user and root;
- that `sshd -T -f <test config>` follows the staged config's absolute `Include` as described;
- end-to-end delivery: the `SendEnv` values present in a `claude`/`shell --macos` session, and absent from
  a plain `ssh`;
- a real guest's process list during a session;
- the BSD-userland behaviour of the push (`find -mmin`, `umask`, `mv`) and of the root script
  (`mktemp`, `grep -qxF`, `awk`), which test 56 exercised with GNU tools.

## Contract vs code

No divergence on I10's argv property: the only credential-bearing ssh puts names, never values, on argv,
and test 56 enforces it through a real `ssh` shim. Wording nuances, none with mark impact:

1. **INVARIANTS states an unverified host fact as part of the Rule.** "macOS serves a process's
   environment only to its own user and root" appears in the Rule (`:176-178`), while ADR-0023 lists it
   under "Not yet observed on a Mac". It is a residual-risk statement, not something the code enforces.
2. **"Every other child never holds them"** (ADR-0023's Decision, the `ssh_macos_session` comment) is true
   only for file- and `gh`-sourced values; see Residual risks. INVARIANTS and test 56 use the correct,
   narrower form.
3. **The Rule's "a guest without it is refused before any credential is sent"** holds on every path. On
   the running-VM path the refusal comes *after* the non-secret `~/.augur-env` rewrite in the same ssh
   session, on purpose, so old credentials are scrubbed first. INVARIANTS does not mention the scrub;
   ADR-0023 does.
