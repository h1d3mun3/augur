## 1. Essence

augur egress control is unchanged in shape from 2026-09-05: it is still a **host-side, fail-closed, on-by-default domain allowlist**, enforced by **augur-proxy** (a sudo-free Swift forward proxy running as the ordinary host user) re-resolving every connection by hostname against a union-only, three-layer allowlist, with Apple Container severing the guest from direct egress via a host-only network plus `--no-dns`/`--cap-drop` and the macOS VM doing the same via gvproxy's SOCKS-forcing, `--dns-allowlist`, and `--deny-direct`. Nothing in this cycle touched that datapath: `augur-proxy/`'s tree hash is unmoved for a fourth consecutive snapshot, `augur.conf` is untouched, and the gvproxy patch's allowlist-gate-before-forwarding ordering was re-verified line-by-line after a forced rebase and still holds. Everything that landed since 2026-09-05 is VM/container *lifecycle* work orthogonal to the boundary — unattended macOS base-VM provisioning with its password correctly kept off argv and pushed only over stdin, a diagnostic hint for a stale cloned password, and a host-timezone injection into both guest kinds (with a same-day fix removing an over-broad container-recreate trigger the first version of that injection introduced). The one operationally relevant new fact is a new host-side secret file, `~/.augur/macos-admin-password` (0600), which sits at the same trust tier as the existing `~/.augur-env` credential push and adds no new sudo grant beyond what ADR-0007 already accepted for the guest admin account.

### 2.1 Base-image custom provisioning

Unchanged since baseline, re-verified at `augur:4417-4419` and `:4900-4969`. An operator can pre-install extra apt packages into augur's *shared*, host-global container image at build time via `~/.augur/provision/container-packages.conf` (a flat package-name list), gated end to end: presence requires actual non-comment content (`provision_container_packages_present`, `:4907-4910`, so an untouched scaffold adds no `--build-arg` and no prompt), every line is validated against a closed charset (`provision_package_name_valid`, `:4417-4419`, shared with the macOS manifest grammar) via `provision_container_packages_validate` (`:4912-4920`), and the file is TOFU-approved by content hash before it can affect a build (`check_container_provision_approved` → `tofu_decide`, `:4936-4940`). `container_provision_prepare` (`:4951-4955`) runs both checks and — per its own comment — must be called **directly**, never inside a `$(...)`/`<(...)` subshell, because an `exit` there would otherwise only kill the subshell and let an unapproved build proceed unprovisioned. Approved packages become one `--build-arg EXTRA_APT_PACKAGES=…` (`container_provision_build_args`, `:4963-4969`), consumed by `cmd_build` (`:1751-1763`) and `cmd_install_cert` (`:2593-2597`).

The trust boundary is structurally simpler than its macOS counterpart, and the code says so explicitly (`:4900-4903`): this build is a one-shot `eng build` that **already runs with zero egress filtering** (pre-existing, unchanged) — there is no dedicated proxy/gvproxy pair standing over it the way the macOS root hook runs over one. So the container manifest is a closed, code-execution-free grammar (bare package names only) whose only real exposure is "the image build's network is unfiltered by design," not an allowlisted egress hole. **No test file references `container-packages.conf`, `provision_container_*`, or `provision_package_name_valid`** — re-confirmed this cycle (`grep -rl` over `tests/*.sh` still returns nothing) — so this path stays TOFU-gated and grammar-checked in code but exercised by no offline or live test.

### 2.2 Custom CA trust (`augur install-cert`)

Unchanged, and still inert to the egress boundary — re-verified by grep against the current tree rather than resting on byte-identity: `grep -rniE 'tls|ssl|certific|x509|trust' augur-proxy/Sources` still surfaces no TLS-termination site, only ClientHello *parsing* (`SNI.swift:3`, "we never decrypt"), the CONNECT blind-tunnel case (`ProxyRequests.swift:22`), and a "not a TLS record" method-line check (`:64`) — and this is now doubly confirmed, since `augur-proxy/`'s tree hash is unchanged over the whole range. A guest-trusted CA only ever affects what the guest's *own* TLS clients accept **after** the proxy's tunnel is established; the proxy's by-hostname allow/deny decision happens earlier and cannot be influenced by trust-store content.

`validate_cert_file` (`augur:2517-2535`) fails closed on anything but a single well-formed PEM X.509 `.crt` (missing `openssl` included), and `confirm_cert_install` (`:2541-2569`) requires either a real-TTY `y/N` or `AUGUR_ACCEPT_CERT_INSTALL=1` — it refuses non-interactively otherwise. `cmd_install_cert` (`:2576-2610`) base64-encodes the cert and re-runs the same `container_provision_prepare`/`container_provision_build_args` path as §2.1 (`:2594, :2596`) with an extra `--build-arg AUGUR_CA_CERT_B64=…`, consumed by the Dockerfile's inert `ARG`/`RUN update-ca-certificates` block (`Dockerfile:119-124`). It still rejects a trailing `--macos` so a cert meant for the VM can't be silently baked into the Linux image instead (`:2580-2585`), still warns the image tag — and therefore the trust — is shared by every project on that Swift tag (`:2589-2590, :2609`), still warns that a later `build`/`update` rebuilds the image clean and **drops** the CA (`:2607`), and still calls `invalidate_persisted_container` so the rebuilt image actually reaches the next `up` (`:1771-1784`, called at `:2608`). `tests/05_install_cert_unit.sh` is byte-identical to the baseline and passes **7/7** in this checkout (verified this run).

### 2.3 Container lifecycle: persist-and-reconcile

Unchanged in mechanism since #114/#128; re-derived at `e1f00be`, not copied forward. The one delta in range is cosmetic: `feat(container): inject the host's timezone` (`45c9e3b`) added a `TZ=$(host_timezone)` `-e` to `cmd_up`'s `run_args` (`augur:2177`) and briefly folded it into `container_fingerprint`, then `fix(container): drop tz= from container_fingerprint` (`c3ef0a3`) removed it again the same day — fingerprinting it would have forced a hard recreate (`down && up`) on a traveling host that merely changed zones, so TZ now lives only in the baked `run` value plus a per-`exec` refresh in `cmd_claude`/`cmd_shell` (`:2367`, `:2394`). It touches no egress, credential, or mount input and does not change anything below.

- **`down` STOPS and keeps** the container and its egress network (`cmd_down`, `augur:2455-2481`; only `stop_proxy` runs, no network teardown — the network is deliberately kept so the persisted container can re-attach). **`destroy`** (`cmd_destroy`, `:2488-2505`) is the full-removal counterpart: it force-removes the container, drops the fingerprint file, tears down the whole egress datapath, and drops the carried-over prompt history — the clean-guest button.
- **`up` on a stopped container with a matching fingerprint** re-ensures the network, `eng start`s it, then runs `finish_up` (`:2132-2142`); a start failure falls through to a clean recreate (`:2141`).
- **`up` on a RUNNING container reconciles** rather than no-opping (`:2096-2121`): the TOFU gate re-runs, a deliberately redundant `write_merged_allowlist` lands a revocation even on the refusal path (`:2103`), and a mismatched `container_fingerprint` is a hard `exit 1` (`:2114-2118`) — comment: "a running container cannot be re-provisioned" (`--network`/`--cap-drop`/`HTTP_PROXY`/`--no-dns`/credentials are baked once at `container run`). Only on a match does it reach `finish_up` (`:2119`).
- **`finish_up`** (`:2058-2077`) is where all three `up` paths converge: under `egress_enabled` it runs `start_egress_proxy` then `verify_egress_locked` (`:2059-2061`) before the profile-apply step, so the boot tripwire can't be delayed or masked.
- **`container_fingerprint`** (`:1823-1865`) hashes egress mode, the *stable* wiring inputs (subnet, gateway override, proxy port — not the live-inspected gateway, to avoid false mismatches), memory, workspace/mount paths, the profile mount path, every resolved auth value, and `gh auth token` — anything baked into `container run` argv that can't be changed on a running or persisted container without recreating it. TZ, per above, is deliberately excluded.
- ***Caveat carried forward, still inferred and still not exercised — no container engine is available in this environment:*** the fingerprint does not cover `egress_network_name()`, and `AUGUR_INTERNAL_SUBNET`/`AUGUR_PROXY_HTTP_PORT` retain `${VAR:-}` override forms, so an operator who pins both mid-session would see no recreate while `ensure_egress_network` (name-only existence check) creates a second, hash-named network alongside the old one.

**What mechanically enforces the boundary.** The containment argv built under `if egress_enabled` in `cmd_up` (`:2183-2202`) is: attach to the per-project `--internal` network (`--network "$(egress_network_name)"`, `:2187`, created `--internal` so it has no external route at all); `--cap-drop NET_ADMIN` (`:2188`, root-in-guest cannot re-route); `HTTP(S)_PROXY` pointed at the host-only gateway (`:2189-2191`); and `--no-dns` (`:2201`, empty `/etc/resolv.conf`, no resolver to smuggle a query through). On top of that argv, `verify_egress_locked` (`:1386-1429`) runs on **every** `up` via `finish_up` and is the live backstop: it probes seven distinct direct-egress targets (IPv4 and IPv6, ports 80/443) with `PATH` pinned to system dirs so a persisted guest's `~/.local/bin` can't shadow `curl` (`:1409-1419`), probes that external DNS resolution fails, and probes that the proxy itself answers an HTTP status through the configured `-x`; **any** leak sets `leaked=true` and force-removes the container and tears down egress before `exit 1` (`:1423-1427`) — the mechanism, not the argv alone, that makes a container in a bad state unusable rather than silently insecure.

**What is documented but not enforced**, re-measured this cycle rather than assumed carried forward: `INVARIANTS.md` I8's note flags that this containment argv itself is asserted by no test, and the mutation was re-run fresh (not trusted from the prior snapshot) — deleting `run_args+=(--no-dns)` and separately neutralizing `--cap-drop NET_ADMIN` in a clean `git archive HEAD` export both still leave `bash tests/run.sh` **ALL GREEN (28 scripts)**. The structural reason is unchanged: every offline construction test drives `up --no-egress` (`tests/11_construct_container.sh`, confirmed this run to assert nothing about `--network`/`--cap-drop`/`--no-dns`), so the `if egress_enabled` block never executes offline at all; `tests/22_egress_failclosed.sh`, the one suite that would exercise it against a real bind, self-skips without `AUGUR_TEST_LIVE=1` (confirmed this run: `0 passed · 0 failed · 1 skipped`, no container engine in this Linux environment). `INVARIANTS.md` is byte-unchanged over the whole range, so nothing in this cycle moved that boundary in either direction.

### I7, in full

**Rule** (`INVARIANTS.md:89-96`, unchanged this cycle — `git log 697f1f0..HEAD --
docs/security-reviews/INVARIANTS.md` is empty): the merged allowlist is written host-side outside
the project tree; a project's `./.augur/allowlist.conf` is merged only after TOFU approval and only
its sanitized domains; every per-project egress host-state file is keyed on the **full workspace
path**, so one project's approval can never reach another's live proxy.

- **Written outside the project tree:** established above — `proxy_allowlist` resolves under
  `$AUGUR_DIR/proxy`, and that directory is not among the four macOS `--dir=` shares nor the
  container's single read-write bind.
- **Sanitized before merging:** `write_merged_allowlist` never touches the live `AUGUR_PROJECT_CONF`
  directly — it reads only `$(project_conf_hash_file).domains`, a file that `write_project_snapshot`
  (`augur:903-…`) populates exclusively from `project_conf_domains`'s output, i.e. already
  `conf_line_valid`-filtered. There is no code path from the guest-writable file to the merged
  allowlist that skips that gate.
- **Full-workspace-path keying:** `proxy_allowlist`, `project_conf_hash_file`, `proxy_pidfile`,
  `proxy_logfile` are all `$(workspace_slug)-$(workspace_path_hash)` (`augur:767-768,774,1106-1109`)
  — never slug alone. The comment at `:769-773` states the failure this prevents by name: two
  same-basename projects (`~/work/app`, `~/archive/app`) sharing one merged allowlist, "whichever
  ran last" owning both projects' egress. `workspace_path_hash` (`:1029-1037`) hashes the full
  `$WORKSPACE_DIR`, and its own header (`:1009-1028`) restates the rule this section is built on:
  guest-visible names stay slug-based, but every **host-namespace** identifier — including this one
  — carries the hash.

### New this review

44. **[LOW–MEDIUM — new: a real secret now travels through an exposure path only ever accepted
    for a public one] ADR-0018's generated admin password is embedded in `sudo -S` command
    strings passed as a single argv element to a locally-invoked `ssh`, at five call sites, none
    hardened the way the build-time password just was.** Every non-key-auth privileged call
    against a macOS guest follows the shape `ssh_macos "$vm" "echo '$(macos_admin_password)' |
    sudo -S -p '' …"` — `augur:2946` (build sudoers grant), `:3307`
    (`install_macos_managed_settings`), `:3475` (`sync_macos_guest_clock`), `:3539`
    (`sync_macos_guest_timezone`, new this cycle), `:4881` (`run_base_provisioning`'s temporary
    grant). `ssh_macos` (`:642-672`) forwards that whole string as `"$@"` to a local `ssh`
    process — i.e. it is a literal argv element of a process running as the invoking user, readable
    by any co-resident `ps`/`/proc` for the life of that one `ssh` call (typically sub-second: a
    `sudo -S bash -c '…'`, a `date`, or a `systemsetup` round-trip, not the multi-minute boot the
    build-time exposure lasted).
    Before ADR-0018 this was accepted by construction: the embedded value was always the fixed
    `admin`/`admin` string, which ADR-0007 itself calls "the already-public password" — there was
    nothing to leak. ADR-0018 changes exactly this precondition on a macOS 27+ host building a
    macOS 27+ guest: `macos_admin_password()` (`:617-621`) now returns a 128-bit-entropy
    `openssl rand -base64 24` value read from `~/.augur/macos-admin-password` — a real secret — and
    every one of these five call sites keeps embedding it in the same local-argv shape the build
    password was pulled out of in the very same PR stack (`933f0ee`, closed above). The ADR's own
    "Why base64" rationale explicitly reasons about this string's *shell-quoting* safety (no `'` in
    the alphabet, so the single-quoted `echo '<password>'` can't be broken out of) but does not
    address its *argv-observability* — the exact axis `933f0ee`'s commit message reasons about for
    the sibling build-time exposure ("argv is observable... for the whole life of the boot").
    ADR-0018's Consequences section states the new file is "exactly as sensitive as the fixed
    admin/admin credential it replaces... no change to augur's broader secret-storage model" — true
    for the *storage* model (mode-600 file, correctly created via an `umask 077` subshell with no
    permissive window, unlike item 33's guest-side race), but the *transport* model for these five
    ongoing calls did change underneath that claim: a guessable constant became a real secret
    without the corresponding transport hardening.
    Why this stays Low-to-Medium rather than higher: (a) the exposure window per call is brief —
    these are one-shot commands, not a boot; (b) it inherits the single-user-host premise item 8/33
    already carry, unexamined for a shared host like the rest of that family; (c) per ADR-0018's own
    argument, the guest side gains nothing extra from seeing its own admin password (passwordless
    `sudo` is already granted) — the incremental risk is purely host-side, to a co-resident process
    on the operator's own machine. Not fixed, not tracked as an open issue as of this review. The
    straightforward remedy mirrors `933f0ee`'s own fix: route these five calls' `sudo -S` input
    through the connection's stdin (a second SSH channel or a `printf … | ssh_macos …` pipe,
    analogous to `install_macos_managed_settings`'s existing two-call stdin-for-payload pattern at
    `:3300`) instead of interpolating the password into the command string at all.
45. **[UNVERIFIED TAIL FROM ITEM 43, NOW RESOLVED — verification, not a code change] The gvproxy
    SOCKS-dial timeout does fall back to a sane 30 s when augur leaves `TCPConnectTimeout` unset.**
    The 2026-09-05 review flagged that augur never sets `configuration.TCPConnectTimeout` and could
    not determine, without a Go toolchain, what deadline `socksDial` (item 43's same-day fix,
    `423a7d4`, unaffected by either of this cycle's two repins — `SetDeadline`/`DialTimeout` call
    sites confirmed byte-identical by diffing the patch) actually enforces as a result. This review
    had both a Go toolchain and network access and checked it directly: cloning the pinned
    `b6bb07ed` upstream commit, `pkg/services/forwarder/tcp.go`'s `TCP()` guards the parameter
    **before** any of augur's patch code runs — `if connectTimeout <= 0 { connectTimeout =
    defaultTCPConnectTimeout }` (upstream, unpatched, 30 s) — and augur never passes a CLI flag or
    config file that would set `TCPConnectTimeout` to anything else, so `time.Duration(0)*time.Second`
    (Go's zero value) is what reaches `TCP()`, which immediately replaces it with the 30 s default
    before it is threaded into `socksDial`. Independently confirmed the alternative failure mode
    feared is not live either: a throwaway `net.DialTimeout(addr, 0)` behaves as "no dial timeout"
    (not an instant failure) in stock Go, and `SetDeadline(time.Now().Add(0))` — the shape that
    *would* apply if the zero ever reached `socksDial` unguarded — was verified experimentally to
    fail the very next read/write, which upstream's guard prevents from ever being reached with a
    zero value. Net effect: the availability gap item 43 closed (`423a7d4`) is fully closed, with a
    real, bounded, sane timeout, not one this review has to leave as an open question — this is a
    verification-only update, not a code change, and item 43's own text above is otherwise
    unaffected (both repins since left the socks-timeout code untouched).

### Summary

No large mechanism moved this cycle — `augur-proxy/` and `augur.conf` are byte-identical
throughout, and the two gvproxy repins (`50edb65e`, dependency-only; `b6bb07ed`, a hand-rebased DNS
struct change) preserve every egress-relevant property they touch, confirmed by reading the rebased
hunks directly rather than trusting the commit messages: the allowlist gate in `dns.go` still runs
before upstream's new SOA/PTR/CAA-forwarding switch, and the SOCKS-dial timeout fix from the last
review's item 43 is not only untouched but, for the first time, independently verified end-to-end
(item 45) — this review had a Go toolchain and network access no predecessor had. The one
substantive new finding is item 44: ADR-0018's macOS-27 unattended provisioning turns the
long-accepted fixed `admin`/`admin` credential into a real per-host secret on qualifying hosts, and
while the *build-time* exposure of that secret was caught and fixed in the same PR stack
(`933f0ee`, now "Closed since 2026-09-05"), the five *ongoing* `sudo -S` call sites that authenticate
against a running clone with the same credential were not given the same treatment — a real secret
now flows through a local-argv transport that was only ever safe because the value it carried used
to be public. That gap is genuinely new, plausibly Low-to-Medium (brief exposure window,
single-user-host premise, no incremental value to the guest side), and unfixed as of this review.
Three existing items (24, 26, 27) gained a small, mechanical blast-radius increase from the
companion timezone-sync feature riding the same call shape as the existing clock-sync — same class
of residual, one more call site each, nothing new in kind. Everything else re-checked this cycle —
items 1–3, 5, 8–17, 19–23, 25, 28–35, and every "checked and refuted" entry — is confirmed unaffected
by `git diff --stat` scoping (the referenced file or region is untouched in `697f1f0..HEAD`), not
silently carried. The honest frame is unchanged from every prior review: no live macOS guest ran in
this one either — `tests/e2e_macos_vm.sh` was not exercised, and ADR-0018's own text names three of
its four amended defects as ones only a real first boot surfaced — so the automated-provisioning
path's live behavior rests on its authors' own account plus the offline pure-function coverage
(`tests/41`, `tests/42`, 774 assertions total, 0 failed this run), not on this review having booted
one.
