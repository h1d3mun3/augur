## 1. Essence

augur egress control is a **host-side, fail-closed, on-by-default domain allowlist** that confines a
possibly prompt-injected coding agent (Claude Code today), running on a trusted single-user host, by
forcing *all* guest outbound traffic through **augur-proxy** — a dependency-free Swift forward proxy
that runs as the ordinary host user **with no sudo**. The guest is severed from direct egress and its
only route out is the proxy, which re-resolves each connection **by hostname** and admits it only if
it matches a **union-only, three-layer domain allowlist** (managed baseline + user-global +
per-project); everything else is denied and logged. Egress is on by default (`AUGUR_EGRESS=auto`,
`augur:88`), unrecognized values fail *on* (`egress_enabled`, `augur:672-677`), and the same
allowlist/enforcement contract is shared across both engines — literally so on the DNS side, where
gvproxy's matcher is a declared byte-parity Go port of the proxy's Swift one
(`gvproxy/augur-egress.patch:166-169`). The design principle is **containment, not
exfiltration-proofing** — a formally closed decision
([ADR-0008](../decisions/0008-exfiltration-ceiling-accepted.md)).

**The shape is unchanged since 2026-07-26, and this time that is the whole story on the datapath.**
Everything the predecessor established about *enforcement* carries forward without amendment, because
the four files that implement it are byte-identical. What this cycle landed is a mitigation for a
defect **beside** the boundary rather than on it: a macOS guest's virtiofs client serves stale file
data indefinitely, so augur now invalidates the guest's page cache for the files the host changed
(#124/#135, ADR-0016). That mechanism moves no policy, opens no port and adds no route — but it is
+454/−3 lines of new code in an egress-core file (`git diff --numstat 744638a a626076 -- augur`; the
whole-cycle delta is +486/−4), it runs on every attach and every 5 s thereafter, and it introduces a
host process whose lifetime the I1 teardown does not yet govern (#156). One change *is* on the
boundary and strengthens it: an unresolvable SSH transport now fails the macOS boot self-test
**closed** instead of terminating `up --macos` above the teardown (#137). One change *removes* guest
exposure: the `gh-config` share is gone (#144).

Three things a reader should carry from here into everything below.

1. **The evidence for I1's *boot tripwire* is sharply unequal between the engines, and this review
   measured it rather than restating it.** Deleting `verify_egress_locked`'s call from `finish_up`
   leaves all 29 offline scripts and all 895 assertions green; deleting the macOS teardown fails 35
   assertions across two scripts. The two halves sit under one shared ✅ badge on evidence differing
   by 35-to-0. The contract already concedes this at `INVARIANTS.md:45-48`.
2. **The *containment argv* — the flags that ARE the enforcement — is guarded by no test on
   *either* engine.** That is a carry-forward (§6 item 32, `INVARIANTS.md:79-80` and `:122-126`), now
   measured for every call site rather than one, and extended to two flags the contract's list does
   not name.
3. **Nothing in this review exercised a real guest.** No live tier ran; `make e2e` did not run. The
   msync behaviour the mitigation rests on is a measured property of a closed Apple kext
   (`com.apple.driver.AppleVirtIO`, ADR-0016:53), not a contracted one. That is the honest frame for
   everything below; see §5 PARTIAL.

*elements* are unchanged from 2026-07-26 on **both** engines; what changed is the macOS self-test's
transport handling, and what this review *measured* is how little of either row is machine-checked.

pointed at the wrong VM sweeps one project's shares against another's marker (`tests/43:12-14` says
exactly this). Period: `_MACOS_REFRESH_INTERVAL="${AUGUR_MACOS_REFRESH_INTERVAL:-5}"` (`:3637`) — a
**new operator-settable environment variable**, on no `conf_line_valid` grammar, documented only in
ADR-0016 (§4 at `:125`, §5.2 at `:181`, and §5.3's inventory table at `:197`) and nowhere in the
README. Each tick runs `refresh_macos_shares "$vm" quiet` (`:3670`), which suppresses the routine
report but deliberately not the warnings. **An idle tick costs zero SSH round trips** (the `n == 0`
early return at `:3465` fires before the single round trip at `:3469`), and a non-empty sweep costs
exactly one regardless of how many files changed. It is not free on the host, though:
`macos_vm_running` (`augur:512-514`) is `"$VM_CLI" list | awk | grep -qx` and the loop calls it
**twice per tick** (`:3665`, `:3667`), so an idle tick is two `augur-vm list` subprocess pipelines
plus one `find` per share root — roughly 1,440 `augur-vm list` executions per hour for the life of
the VM. The in-code note that "an idle session costs one `find` per interval and zero round trips"
(`:3625-3626`) counts only the sweep. Termination: the loop exits by itself within one tick of the
guest disappearing, so a crashed augur, a `kill`ed VM or a host reboot cannot leave it sweeping a
guest that no longer exists (`tests/43` pins this).

`sleep "$_MACOS_REFRESH_INTERVAL"` (`:3666`) is unguarded, so a non-numeric

skips `:3672` — leaves a **stale pidfile** behind (measured: "loop alive: NO (stale pidfile left
behind)", log = `sleep: invalid time interval: abc` plus BSD `sleep`'s usage banner).
`share_refresher_running` correctly reports not-running (`kill -0` on a dead pid), so the next `up`
restarts it and it dies again, silently; `start_share_refresher` still returns 0, so `up` is
unaffected and the tripwire is still reached. (b) The logfile is append-only, never rotated, mode
**0644** under the default umask (the same posture §6 item 28 flags for the proxy decision log), and
is reaped only by `destroy --macos` (`:4169`), never by `down --macos`. A persistently failing
refresher writes two lines per tick — measured between 154 and 265 bytes depending on which arm fires
and how verbose the ssh error is — i.e. ~1,440 lines and very roughly 110–190 KB per hour at the 5 s
default, with ANSI colour bytes (unconditional: `augur:18-23` has no TTY or `NO_COLOR` test) and
host-side file names in it. This is the first augur host-state file that grows while nobody is
watching it.

**The new guest round-trip surface.** The sweep is one call:
`ssh_macos "$vm" "python3 -c '$(_macos_msync_program)' 3 5" < "$list"` (`:3469`). The program
(`:3356-3400`) is ~1.4 KB / 41 lines and **contains no single quote** (`tests/41` pins this), which is
what lets it be wrapped in one for the remote zsh; the two argv integers are `_MACOS_SWEEP_TRIES=3`
(`:3328`) and `_MACOS_SWEEP_DETAIL=5` (`:3332`), both script constants. The path list travels on
**stdin, NUL-separated** (`:3460`), never on argv — and that choice is load-bearing for more than the
"bash strings cannot hold NUL" reason the comment gives. The workspace and both per-VM `claude-*`
shares are mounted read-write, so a compromised guest can create files whose names the host's `find`
will enumerate and hand straight back into the guest. Because they are split by
`sys.stdin.read().split(chr(0))` and never by a shell, a hostile filename cannot escape the protocol,
and APFS cannot produce a NUL in a name. Had those paths gone on argv, this would have been a
guest→host→guest command-injection channel. See §6's refutations.

**I10 is unaffected** (`INVARIANTS.md:143-148`). Nothing this series puts on a command line is a
credential: the token push is still the stdin pipe at `augur:3961-3971`, still 56 lines **after** the
tripwire on the fresh path, and the reconcile branch injects no credential at all. What changed is
volume, not kind: the ~1.4 KB program string is now in the host's process table once per non-empty
sweep and in the guest's as `python3 -c '…'`. The M1 residual (`container run -e` on the container
path) is untouched, and `grep -c 'sudo -S' augur` is 9 at both revisions — the series added no
privileged guest command.

**The tripwire's probe dotfile** is `.augur-freshness-probe` (`:3528`), written host-side into
`$AUGUR_DIR/claude-agents/<vm>/` (`:3531`, `:3551`, `:3583`) and read at
`/Volumes/My Shared Files/claude-agents/.augur-freshness-probe` (`:3532`); overwritten rather than
deleted, in a directory augur owns and that Claude Code only scans for `*.md`. Three things about it,
all of which matter more than the mechanism:

- **It is a platform-behaviour probe, not a security control, and cannot be made into one.** The share
  is read-write and the guest can read the very value the host just wrote, so a compromised guest can
  forge every verdict the tripwire has — **six** printing outcomes, not four: `:3546` (no SSH
  transport), `:3578` (the guest cannot read the probe), `:3594`, `:3599`, `:3608` and `:3611`. The
  code says as much (`:3521-3524`) and ADR-0016 §5.1 says "No invariant asserts freshness", which is
  the right call — but the word "self-test" should not mislead a future reader.
- **Its probes do not pin PATH, and neither does the sweep.** All four tripwire probes invoke bare
  `python3`/`cat` (`:3573,3574,3584,3587`), and so does the sweep's own round trip (`:3469`) — unlike
  `verify_macos_egress_locked` one function away, whose `pp='export PATH=/usr/bin:/bin:/usr/sbin:/sbin;'`
  (`:1526`) exists precisely because "`~/.augur-env` puts `$HOME/.local/bin` FIRST in the PATH of
  every guest shell" (`:1519-1525`; augur writes that line itself at `:3964`, sourced from `~/.zshenv`
  at `:3973`). A guest that plants `~/.local/bin/python3` therefore decides both what the tripwire
  reports **and** what the sweep reports — including a fabricated `ok=N` while nothing is invalidated,
  and the ADR-0016 §5 removal signal at `:3605-3609`. §6 item 39.
- **The host writes into it by name, and the guest can write that directory.** `augur:3834` mounts
  the per-VM `claude-agents` share read-write (no `:ro`, unlike `:3835`). A symlink planted at that
  name would make `printf … > "$host_dir/.augur-freshness-probe"` truncate and overwrite a host file
  outside the share; measured in a host-side harness (29 → 19 bytes, function still returning 0), and
  `grep -c noclobber augur` is 0. Content is host-chosen, so this is a truncate/clobber primitive, not
  code execution — **and the guest half is not verified**: whether a VZ virtiofs guest can create a
  symlink in that share was not tested here. It is recorded because it re-instantiates the class the
  predecessor RETIRED at `2026-07-26-egress.md:866-875`, and because `destroy --macos` never clears
  that directory (§6 item 22), so a planted link would survive into the next clone. §6 item 39.

Two in-code numbers this review could not confirm, both cosmetic but both now wrong in a comment a
future reader will trust: `augur:3537` says the probe file "is 40 bytes" — the format is
`probe-$$-${RANDOM}-a`, measured 19 bytes and capped at 20 — and `augur:3526` says the tripwire costs
"three extra round trips" when it makes **four** (a claim `tests/42:282`'s message repeats). Filed as
part of #157's family; see also `augur:3341`/`:3323` on the share count. Separately, ADR-0016 (and
`augur:3310`) states the host-side `find` costs 0.31 s and that the same walk from inside the guest
costs "~15× that". From inside this guest a warm `find -type f` over the workspace share returned
13,045 files in **0.54 s**, which does not reproduce a 15× gap — not a refutation (the ADR's figure is
presumably cold and there is no host shell here to re-measure the 0.31 s side), but the 15× claim is
the sole justification for "host finds, guest invalidates" and rests on one unrepeated measurement.

### 2.5 Workspace containment: what `require_safe_workspace` does and does not cover (unchanged)

Unchanged in substance; every anchor re-derived and the mutation proof re-run (M11 above).
`require_safe_workspace()` (`augur:983-1023`) refuses a workspace that **is**, **contains**, or
**lives inside** `$HOME` or `$AUGUR_DIR` (or is `/`), comparing **physical** paths via `pwd -P`
(`:985-997`). Three properties to keep in front of a future reader:

(a) it is gated to `up|claude|shell|setup-token` only, at the single dispatch-tail call site
`case "$COMMAND" in up|claude|shell|setup-token) require_safe_workspace ;; esac` (**`augur:5433`**,
was `:4951`), by design — `down`/`destroy`/`list`/`status`/`build`/`update`/`install-cert` stay
ungated so a guest a pre-fix augur created from `$HOME` can still be removed (ADR-0014:153-169);

(b) it does **not** re-base `WORKSPACE_DIR` — the physical paths are computed locally inside the
function on purpose (`:976-982`), because `workspace_path_hash` (`:952-960`) feeds container names, VM
names, the TOFU approval key and every per-project state dir, so re-basing on `pwd -P` would silently
rename all per-project state for anyone whose path crosses a symlink;

(c) there is deliberately **no** escape hatch, and relocating `AUGUR_DIR` is not a workaround, since
it is an unconditional assignment (`augur:41`) and `~/.augur` stays on PATH via the shell rc
regardless.

The mechanism it closes is stated in-code at `augur:962-975`: `$WORKSPACE_DIR` is shared read-write on
both engines, `install` puts `~/.augur` **first** on the host's PATH, and it holds the `augur` /
`augur-proxy` / `augur-gvproxy` / `augur-vm` binaries that `resolve_proxy_cli`/`resolve_gvproxy`
execute **as the host user on every `up`**; secondarily, with `WORKSPACE_DIR=$HOME` the merged
allowlist under `~/.augur/proxy` sits inside the read-write share and is hot-reloaded every ~2 s —
which the code calls "a direct I7 violation" (`:972-973`).

**Not extended by the #124/#135 series, and worth stating explicitly.** `macos_share_roots`
(`augur:3344-3350`) walks `$WORKSPACE_DIR` and three `$AUGUR_DIR` subtrees to build the sweep list,
so the new refresher reads paths under `~/.augur`. That is a host-side `find` over host-owned
directories; it adds no new path into the guest and no new writable surface, and it does **not**
include `$AUGUR_PROXY_DIR`, so the merged allowlist is not in the sweep. The guard's coverage is
therefore unchanged by this series, not merely unbroken by it. **Note the contrast with §2's mutation
table:** the workspace guard, which is not an egress mechanism, is better covered offline than either
engine's egress containment argv.

## 6. Known limitations & residual exfil channels

The threat model is *"contain a prompt-injected agent away from its host,"* **not** *prevent exfil
through a legitimately allowlisted, credentialed host*. **All 35 of the predecessor's numbered entries
are re-emitted** — items 1–6 and 8–35 as live residuals (34 of them), items 7 and 12b as closures —
each re-derived against `a626076` rather than copied, because `augur` grew 486 lines and every anchor
above `augur:3255` moved by 431 or more. Nothing in §6 closes this cycle; one defect that **no**
snapshot had named does close (below). **Seven items are new (36–42)**, all from the #124/#135 series
or found while reviewing it.

The load-bearing structural fact for this section: `git diff --name-only 4041c31 a626076 --
augur-proxy gvproxy augur.conf augur-vm` returns **empty**, so items 10, 19 and 23 hold mechanically
(re-measured anyway: 54/54 Swift green). Note that this does **not** by itself carry items 2 and 29,

1. **Allowlisted + credentialed host is an in-policy exfil surface — a closed, permanent decision.**
   `github.com` allowlisted (`augur.conf:29-31`) + a full-scope `GH_TOKEN` injected (`augur:2185`) →
   an injected agent can push data to an attacker repo entirely within policy.
   [ADR-0008](../decisions/0008-exfiltration-ceiling-accepted.md) (issue #24, closed) declines to
   mitigate this by default or opt-in. **Unchanged.**
2. **Wildcard / QNAME tunneling.** A broad wildcard (`*.githubusercontent.com`, `augur.conf:34`)
   permits `<data>.<wildcard>` leakage; I2's label-boundary anchoring bounds the **match**, not the
   QNAME content. Mitigation is allowlist policy, not the matcher. **Unchanged.** The bound worth
   carrying: on the macOS engine gvproxy admits only `A`/`AAAA`/`CNAME` and refuses every other qtype
   (`gvproxy/augur-egress.patch:113-119`, byte-identical), so the high-bandwidth `TXT`/`NULL`
   **response** channel is closed; container mode has no in-guest resolver at all (`--no-dns`,
   `augur:2078`).
3. **Apple Container host-only host-reach (accepted trade-off).** The `--internal` network
   (`augur:1230`) is "host-only": the guest can reach other host services bound to `0.0.0.0` (raw TCP,
   not proxy-mediated). A direct consequence of the no-sudo constraint; documented, not enforced,
   effectively **permanent** ([ADR-0001](../decisions/0001-sudo-free.md)). #127 renamed the network but
   did not change its routelessness.
4. **No-sudo consequences ripple through the datapath.** Every fix in this series is a refusal, a
   verification or a host-side reorder rather than an escalation. #133's guest-side `sudo -S` with the

   precisely because UDP has no path out (`:3182-3188`). **This series adds no new privileged guest

36. **[MEDIUM — guest→operator terminal; issue #155, and wider than the issue states] Guest-chosen bytes
    reach the operator's TTY through `echo -e`, on the ROUTINE path, in unbounded quantity, with no
    host-side sanitisation.** `_refresh_macos_shares_locked` prints the guest's stdout through
    `warn`/`info`, which are `echo -e "${YELLOW}[augur]${RESET} $*"` (`augur:121-124`). The only
    neutralisation is **inside the guest program** and covers CR and LF only:
    `def disp(q): return q.replace(chr(10),"?").replace(chr(13),"?")` (`:3385`).

    **Three things this review established that the issue does not say.**

    (a) **It is not primarily an `echo -e` problem.** A filename containing a **raw ESC byte** needs no
    backslash interpretation at all — plain `echo` would pass it through. Measured end to end: a file
    named `pwn<ESC>[31mRED<ESC>[0m` in the workspace share, kept growing so the *shipped* guest program
    classifies it `unstable` and names it, produced those ESC bytes in the program's own output, and the
    real `_refresh_macos_shares_locked` then emitted them to the terminal through `warn "  ${detail}"`
    (`:3492`). `echo -e` is a *second, independent* way in: on the stock macOS `bash 3.2.57` `\e` is
    inert but `\x1b` and `\033` are honoured, and on a Homebrew bash ≥4.2 first on PATH `\e` works too —
    so the exposure does not depend on which bash the operator has. (`warn`'s `$*` **is** quoted
    (`:123`), so word-splitting and globbing are not additional vectors — attacked and refuted.)

    (b) **The success path is a sink too.** `$summary` — the guest's first stdout line — is interpolated
    into `info "Refreshed the guest's view of ${n} changed shared file(s) (${summary})."` (`:3495`).
    Measured: a guest returning `ok=1 \x1b[31mINJECTED…` put 6 ESC bytes on the terminal via the
    **non-error** branch. With the *shipped* program `$summary` is a fixed key set, so this arm needs a
    guest that controls `python3`'s stdout — see item 39, which makes that cheap.

    (c) **`_MACOS_SWEEP_DETAIL=5` is not a host-side bound.** The cap is applied inside the guest program
    (`:3383`, `:3394`); the host loop at `:3491-3493` has **no** `head -n` and prints *every* line after
    the first. Measured: a guest sending 500 detail lines produced 501 `warn` lines where the documented
    bound is 7. So the cap is the same class of non-control as `disp()` — a courtesy the guest is free
    not to perform — and both the escape bytes and the line count are guest-chosen. The host also buffers
    the whole stdout into a shell variable (`out=$(…)`, `:3469`), so a deliberately verbose guest costs
    host RAM as well.

    **Exploitation preconditions, honestly.** Vector (a) needs only **write access to the read-write
    workspace share**, which the agent has *by design*. Vectors (b)/(c) need control of the `python3 -c`
    stdout — a compromised guest, or a shadowed `python3` (item 39), which the same actor can plant just
    as easily; there is no meaningful tier separating them. The realistic impact is **display forgery**
    (spoofing an `[augur]`-prefixed line, erasing lines with `\033[2K\r`, colour/title/OSC sequences the
    operator's terminal honours), not host code execution — nothing `eval`s the response; it is only
    `case`-matched and echoed. It is MEDIUM because it is reachable by the actor the threat model is
    named for, on the routine success path, with no operator action, and — through the refresher log —
    every 5 s unattended.

    **Same class as the closed #37, one layer up, and the fix shape already exists in this repo.**
    `DecisionLog.sanitize` escapes every scalar `< 0x20` and `== 0x7F` plus backslash
    (`Logger.swift:66-79`) and is covered by `testDecisionLogSanitizesControlBytesInDeniedHost` (green in
    the 54/54 run). The shell path has neither. Scope note, deliberately: **no invariant in
    `INVARIANTS.md` covers terminal output**, and this is not an egress widening.
37. **[LOW–MEDIUM — availability; a NEW guest→host amplification channel] The 5 s sweep's host-side cost

    (`0016:89-100`) is a four-row table — "Host-side detection 0.31 s (`find -newer`, 12,626 files)",

    both `up --macos` paths (`:3728`, `:3888`) **before** `verify_macos_egress_locked` (`:3741`, `:3905`).
    An abort there is the same shape as the defect `7c5120a` and `9de819d` just closed: `up --macos` dies
    without reaching the egress tripwire, leaving a running VM with a live NIC. It is contained today only
    because `_refresh_macos_shares_locked` returns 0 on every path — an invariant nothing enforces. The
    narrow trigger is the unguarded `printf '…\0' … >> "$list"` (`:3460`) failing mid-scan (ENOSPC, or a
    state dir that turned read-only after the `: > "$list"` probe at `:3455` succeeded); note that a
    stalled — rather than failing — guest is the more reachable variant, since `ssh_macos`'s
    `ConnectTimeout=10` / `ServerAlive 15×4` (`:592-594`) bound a *dead* sshd, not a live one running a
    sleeping command, and a shadowed `python3` (item 39) can stall the sweep at a call site that precedes
    I1's tripwire on both paths. `tests/41_macos_share_refresh.sh` runs entirely under `set +e` (`:39`)
    and calls the function inside `$( … )`; both neutralise the failure mode, so the suite is
    **structurally incapable** of seeing this — the same blind spot `augur:3559-3572` documents and says
    `make e2e` had to catch. One more consequence: inside the refresher loop the same abort exits the
    backgrounded subshell without running `rm -f "$pf"` (`:3672`), leaving a pidfile pointing at a dead
    pid; `share_refresher_running` then reports not-running and the next `up` restarts it, so it
    self-heals across attaches but dies silently for the rest of the session.
41. **[LOW] The fail-closed teardown does not stop the share refresher, and `down --macos` does not reap
    its log (issue #156).** `verify_macos_egress_locked`'s teardown is `"$VM_CLI" stop "$vm"` /
    `stop_gvproxy` / `stop_proxy` / `exit 1` (`augur:1647-1650`) — no `stop_share_refresher`, even though
    both `cmd_down_macos` (`:4097`) and `cmd_destroy_macos` (`:4138`) call it **first** on the stated
    grounds that it is "the only one of the three that would otherwise keep issuing SSH into a guest this
    function is about to stop" (`:4093-4096`). On the reconcile path the refresher is started nine lines
    before the teardown (`:3732` → `:3741`); on the fresh path at `:3896` before `:3905`. Self-healing in
    the normal case — the loop's `macos_vm_running` gate breaks it within one interval — but
    `"$VM_CLI" stop` is `|| true` (`:1647`), so on a stop that failed, the surviving loop keeps SSHing at
    a VM the tripwire has just declared leaky, with gvproxy already gone, appending two `warn` lines to
    the logfile every 5 s indefinitely (that consequence chain is INFERRED; the missing call is OBSERVED).
    Availability cost is bounded and small; **the cost that matters is that the fail-closed path now
    diverges, without explanation, from an ordering rule two sibling functions state in their own
    comments** — and an unexplained divergence in a fail-closed path is how the last one started. The
    issue's own bar is the right one and worth repeating, because the fix looks like a one-liner and is
    not: `stop_share_refresher` returns 0 unconditionally *today*, but any call placed **before**
    `"$VM_CLI" stop` in that block is a call placed inside the I1 teardown under `set -e`, where a
    non-zero return means a live VM with a live NIC. Put it after `stop_proxy`, or guard it. Note also
    that `cmd_up_macos`'s SSH-timeout teardown (`:3863-3866`) does not stop it either — harmless there,
    because on that path the refresher has not been started yet.
42. **[UNDETERMINED — carried out of the "checked & refuted" class on purpose] The one-time Option-A
    history migration `mv`s over a glob inside a guest-writable directory.** `local _pre_option_a_entries=("$host_hist_dir"/*)`
    (`augur:2136`) feeding `mv "${_pre_option_a_entries[@]}" "$host_hist_dir/$agent_proj_leaf/"` (`:2140`),
    in a directory mounted read-write into the guest (`:2143`). A guest-planted symlink or pre-created
    leaf could plausibly redirect or break that `mv`. **This is pre-existing, not introduced by this
    series, and its exploitability was not determined by 2026-07-26 and is not determined here either.**
    It is given a number so it stops living underneath a heading that reads "do not re-investigate" —
    which is where the retired Docker-history refutation would otherwise strand it. Same shape as item
    39(d): a host process writing by name into a share the guest can write.

### Summary

Egress control is unchanged in **shape** since 2026-07-26 — a **host-side, fail-closed, sudo-free
domain-allowlist scheme shared by two engines** (Apple Container + macOS VM), on by default, with a
union-only three-layer merge, TOFU approval, and a Swift filter core — re-verified green at `a626076`:
**54/54 Swift**, `tests/run.sh` **ALL GREEN — 29 scripts, 895 assertions, 0 failed, 4 expected
live-tier skips** (up from 24 scripts / 731 assertions, entirely from the five new `39`–`43` scripts,
of which 130 assertions gate a mitigation no invariant names). `augur-proxy/`, `augur-vm/`, `gvproxy/`
and `augur.conf` are **byte-identical** to the predecessor's tip — verified by tree hash, not assumed
— so §3 and the default-domain set carry forward mechanically. Of the egress core only `augur` moved,
+486/−4 across 12 non-merge commits; the rest of the 43-commit range is tests and docs.

The substance of the cycle is a **mitigation, not a contract change**: ADR-0016's `msync(MS_INVALIDATE)`
answer to the virtiofs staleness defect (#124/#135). `INVARIANTS.md` is deliberately untouched, and
ADR-0016 §5.1 makes that explicit so the mitigation cannot quietly become load-bearing for something
else. **One egress-semantics change did ride along and it strengthens I1**: `7c5120a` gave
`verify_macos_egress_locked` a transport pre-check, closing a path where `ssh_macos`'s `exit 1` jumped
clean over the fail-closed teardown — a hole no prior snapshot had named, and one that only `make e2e`
could have found. **One change reduces guest exposure**: the `gh-config` share is gone (#144).

All 35 numbered residuals carry forward, none has stopped being true, and none was dropped. **Seven
are new (36–42)**, of which the ones a reader should act on are: the **guest→terminal injection
channel** (item 36, issue #155 — measured to be wider than the issue says: it fires on the routine
success path through `info`, its per-file cap is guest-side only and the host prints an unbounded
number of lines, and its most reachable vector needs only workspace write access); the
**guest-chosen host-side sweep cost** (item 37 — the ADR's four cost rows all measure something other
than the loop that dominates); the **unpinned PATH on the sweep's own round trip** (item 39(a), which
turns a guest-planted `python3` into silent defeat of the mitigation *and* into item 36's sink); and
**#154's dead subshell guard** (item 40 — unreachable under `set -e`, sitting ahead of I1's tripwire on
both `up --macos` paths). From the predecessor, the three a reader should still act on are unchanged
and unfixed: the **unguarded `egress_enabled` on the macOS reconcile self-test** (item 24 — now with
four *more* unguarded steps ahead of the teardown, and none of the new output explaining it), the
**unactionable remedy on `require_socket_path_fits`'s hard exit** (item 25), and the **complete absence
of any test guarding the production containment argv on either engine** (item 32, re-proven at this tip
for seven call sites, two of which the contract does not even name). The **RW-workspace `.git/hooks`
host-code-execution path** (item 12) remains the single highest-impact residual; continuous host→guest
invalidation moves it in **neither** direction, but it is what makes item 37 reachable.

Five statements from earlier snapshots are corrected by name: the gvproxy freshness grade (`NOISE`
since 2026-07-22, not `CURRENT`), I9's "structurally pinned offline", item 24's "the only step … is
`sync_macos_guest_clock`", item 26's "immediately before … on both paths", item 31's "exactly three
traps", item 28's "nothing ever removes them", closed-item 7(b)'s "`stop_egress` … reachable solely
from `cmd_destroy`", and 2026-07-23's "Neither widens egress" verdict on the basename-keying bug. Two
in-repo artifacts carry stale anchors of their own and are reported to their owner rather than edited
here: `INVARIANTS.md:107`'s `augur:4951`, and I1's `Enforced by`, which does not name `tests/40`.

And the honest frame is unchanged: **none of this review exercised a real guest** — every macOS
mechanism here is proven by a bash stand-in for `ssh_macos`, by the guest program run for real against
*local* files, by mutation, and by reading; `tests/e2e_macos_vm.sh` remains the only live gate and is
`AUGUR_TEST_LIVE`-gated, and it gained 194 lines this cycle that this review did not run. The one thing
this series can say that no predecessor could is that the live gate **did** run, on real hardware, and
caught two I1 defects the offline suite structurally could not — which is an argument for the gate, not
for the snapshot.
